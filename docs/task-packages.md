# Контракт пакета задачи (formatVersion 1)

[Workflow и CLI](workflow.md). Контракт dwf-oc-xit.1 для контекста (xit.2/3),
implement runtime (xit.4) и UI (xit.5). Это данные существующего workflow/store,
не новый трекер. Beads остаётся внешним источником; DWF не вызывает Beads.

## Публичный ввод

`node ./dwf.mjs start --file workflow.json` принимает прежнюю схему плюс
необязательный непустой массив `taskPackages` и ссылки `nodes.<node>.taskId`.
`node ./dwf.mjs schema` показывает формат. Пример:

```json
{
  "task": "Полный исходный ввод пользователя, не автоматически сочинённая сводка",
  "taskPackages": [{
    "formatVersion": 1,
    "id": "task-A",
    "beadsId": "dwf-oc-xit.1",
    "requirements": "Точное исходное требование\r\nБез сокращения и нормализации.\n",
    "acceptanceCriteria": ["Точный критерий приёмки"],
    "dependencies": [],
    "decisions": [{
      "id": "storage",
      "text": "Использовать существующий store",
      "source": "user:approved-architecture"
    }],
    "artifacts": [{"id": "contract", "uri": "docs/task-packages.md"}]
  }],
  "entry": "work",
  "nodes": {"work": {"role": "worker", "taskId": "task-A"}},
  "transitions": {"work": {"done": null}}
}
```

Все поля пакета, кроме `beadsId`, обязательны. Массивы могут быть пустыми —
DWF не изобретает отсутствующие критерии, решения или артефакты.
`requirements`, критерии и тексты решений — точные Unicode-строки; не trim,
не сводка, не нормализация CRLF/Unicode. Непустота проверяется без изменения
значения. Непарные суррогаты в требованиях и некорректный UTF-8 файла отвергаются.
Проверка UTF-8 действует также при `preset save --file`, до создания или
перезаписи пресета. JSON-экранирование не является частью текста требования; исходные байты самого
JSON хранятся отдельно для аудита. Для корректного UTF-8
`Buffer.from(restored.requirements, 'utf8')` восстанавливает байты требования.

- `id` — устойчивый ID внутри workflow, задаётся автором. Не выводится из имени
  узла, текста, порядка массива или ID Beads. Ссылки между запусками требуют
  также `runId`; глобального реестра задач нет.
- `beadsId` — необязательный внешний ID. ID пакетов и заданные Beads ID уникальны
  в одном workflow; один пакет может обслуживать много участников/посещений.
- ID пакетов, Beads, решений и артефактов: `[a-zA-Z0-9][a-zA-Z0-9_.-]*`, кроме
  `__proto__`, `constructor`, `prototype`. ID решений/артефактов уникальны внутри
  соответствующего массива пакета.
- `dependencies` — уникальные ID существующих пакетов; собственные зависимости
  и циклы недопустимы. В прежнем плоском графе это описание данных: маршруты
  не начинают ждать зависимости автоматически. [Implement](implements.md) использует
  эти же ссылки для реального ожидания интегрированных результатов.
- `decisions` — принятые к старту решения с явным `source` (непустая строка,
  например ссылка на сообщение/документ). DWF не объявляет чужой отчёт решением.
- `artifacts` — устойчивые локальные ID и непустые `uri`: путь относительно
  проектного workspace или внешняя ссылка. Это непрозрачные ссылки, не команда
  чтения. DWF не скачивает их и не требует наличия будущего файла при старте.
  Разрешение ссылок и права чтения относятся к сборке контекста.
- Неизвестные поля пакета, неоднозначные ID и неизвестные `taskId` отвергаются.
  Весь статический контракт проверяется **до** подключения OpenCode, подготовки
  worktree и создания запуска. Динамические `itemsFrom` проверяются до подготовки
  любого дочернего workspace/отправки группы.

`groups.<group>.items[].taskId` (включая динамические `itemsFrom`) явно заменяет
`taskId` шаблонного узла для этого map-элемента. Без него наследуется ссылка узла.
Фиксированная группа использует ссылки своих узлов. В старом workflow без
`taskPackages` произвольное поле `items[].taskId` остаётся непрозрачными
метаданными элемента, как прежде; пакетная семантика включается каталогом. Отсутствие ссылки означает
отсутствие привязки; DWF не угадывает её, даже если пакет всего один. Управляющий
узел может оставаться без привязки.

Системные инструкции роли (`participant.agent.system`), методика скилла и
`nodes.*.instructions` не становятся требованиями пакета. Исходный технический
prompt сохраняется отдельно от `taskContext`. Адресная сборка обычных ролей
реализована в xit.2: [данные, ссылки, UI и проверки](role-context.md).
Версия пакета фиксирует данные посещения, не означает автоматическую проверку
всех требований участником.

## Снимок, уточнения и происхождение

В существующей SQLite `workflows.state` сохраняются:

- `definition.taskPackages` — неизменяемый исходный снимок, версия каждого
  пакета **1** (не путать с версией формата). `definition` пакетного workflow
  также неизменяем: ссылки не могут незаметно переадресоваться.
- `inputSnapshot = {encoding:"base64", data, source}` — полные байты входного
  файла, включая пробелы/экранирование; `source` — путь источника. Старый planner
  сохраняет это в `run.request.inputSnapshot`. Пресет без пакетов сохраняет
  материализованный полный JSON, имя пресета и вложенный `taskFile` с исходными
  байтами/путём файла поручения. Снимки не перечитываются с диска при restart.
- `taskRevisions` — append-only журнал последующих уточнений/решений. Исходный
  текст никогда не переписывается этим журналом.

```sh
node ./dwf.mjs steer <runId> <participant> --message-file clarification.txt
node ./dwf.mjs steer <runId> <participant> --message-file decision.txt --kind decision
```

`--kind` допускает `clarification` (по умолчанию) или `decision`. Это явная
классификация пользовательского ввода, не результат классификатора модели.
Для привязанного адресата при **приёме** команды атомарно с controls добавляется:

```json
{
  "taskId": "task-A",
  "version": 2,
  "kind": "decision",
  "text": "Точное содержимое message-file, включая переводы строк",
  "source": "steer:<command UUID>",
  "createdAt": 1790000000000
}
```

Версии идут без пропусков отдельно для каждой задачи: 1, 2, 3, ... . `source`
ведёт к сохранённой команде, адресату, времени и статусу доставки. Принятое,
но затем отменённое stop уточнение остаётся в аудите; наличие ревизии **не**
доказывает доставку модели. Для непривязанного адресата сохраняется прежний
controls без выдуманной задачи. Результат orchestrator/reviewer сам по себе
не становится изменением требований. Следующие этапы могут использовать
тот же append-only формат для явных решений, сохраняя происхождение.

Посещение и каждый дочерний участник группы сохраняют `taskId`, `taskVersion`.
Версия фиксируется при подготовке входа; уже начавшийся admission не меняет
её после позднего steer. При дополнении ещё подготовленного child его версия
обновляется вместе с prompt. Это ссылка на версию данных, **не delivery cursor**
и не доказательство самостоятельной проверки требований моделью.
В xit.2 привязанный снимок содержит точный пакет; [xit.3](context-delivery.md)
передаёт изменения относительно подтверждённого input той же сессии, сохраняя
полный актуальный снимок и доступ к точным пакетам. Steering map-участнику
сохраняет его пакет при отдельном посещении/отмене подготовленной группы.

Чтение/restart проверяет формат, ссылки, версии и привязки посещений без
миграции/исправления данных. Запись проверяет неизменяемость снимка и префикса
журнала, в том числе после callback `withWorkflowAction`. Уже замороженный
input сохраняет прежние `taskId/taskVersion`; переименование его более поздней
версией отклоняется и для отдельного посещения, и для child группы. Возврат
замороженного ввода в `prepared` также запрещён: сброс маркера admission не
размораживает привязку. Удаление определения/журнала в callback не позволяет
обойти проверки снимка и аудита через совместимость со старым форматом.
Обновления контроллера подхватывают новые ревизии одновременно с
controls, не затирая команды другого процесса. Внешнее действие не выполняется
с некорректным пакетным состоянием. Это не защита от прямого редактирования
SQLite с подменой всех согласованных полей; криптографической подписи нет.

## Точки подключения следующих задач

- `task-packages.mjs`: `validateTaskPackages`, `validateTaskReference`,
  `taskBinding(state, nodeId, item)` и
  `taskPackageAt(state, taskId, version?)`. Последняя функция возвращает копию
  точного исходного пакета, версию и только ревизии до неё (по умолчанию текущие).
  Она не синтезирует «обновлённое требование» из текста уточнений.
- Сборка контекста должна использовать эти поля вместо извлечения требований
  из prompt/summary. Доставка и курсоры — отдельный контракт xit.2/3.
- Runtime implement должен ссылаться на `taskId` того же каталога, фиксировать
  версию для каждого фактического посещения и использовать `dependencies`
  для готовности. Этот потребитель реализован в [контракте implement](implements.md);
  пакеты/версии и сборка prompt остаются общими.
- `getWorkflow`/`savedRuns` дают структурированные данные UI. Публичный `inspect`
  дополнительно выдаёт `taskPackages`, `taskRevisions`, `current.taskId/taskVersion`,
  идентичность children в `current.members`, а также `history`/`history.members`.
  UI должен читать их, не угадывать пакет по именам. Полный сырой ввод доступен
  через store; он не дублируется в каждом watch-update.

## Совместимость и пресеты

Без `taskPackages` прежние графы, planner, controls, сохранённые prompt/результаты
и SQLite schema version 1 поддерживаются. Новые обычные inputs хранят общий
`definition.task` структурированно, без угадывания пакетов. Поля пакетов/версий не придумываются
для raw-only истории. Новых таблиц и обязательной миграции нет.

`preset save --file` и `--from-run` сохраняют исходные пакеты/привязки как часть
определения, но не журнал уточнений/старые сессии. Пакетный пресет можно прочитать
через `preset show`, явно обновить требования/ID и запустить `start --file`.
`start --preset ... --task-file ...` для пакетного пресета отклоняется: замена
только общего task не должна молча повторять чужие точные требования пакетов.
Для старых пресетов команда работает без изменений.

## Проверки

`node --test task-packages.test.mjs` проверяет идентичность, зависимости,
неизвестные ссылки до внешних действий, точные байты текста, неизменяемость,
пропуски версий, чтение в новом процессе и динамические ссылки группы.
Native-тест `public CLI task packages...` в `acceptance/runtime.test.mjs`
проверяет кандидатный CLI с изолированным OpenCode/HTTP provider: аудит полного
ввода, решение с происхождением, restart после принятия ввода, повторение
неизменного input и нужный пакет посещений. Старые записи покрывает общий
`npm run test:product`; весь контур — `npm test`.
