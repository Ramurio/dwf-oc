# Адресный контекст ролей (dwf-oc-xit.2)

[Пакет задачи](task-packages.md) остаётся источником точных требований. Сборка
не извлекает требования из summary и не пытается автоматически разделить общий
`task` на задачи. Автор workflow связывает worker/reviewer/verifier с `taskId`
(либо задаёт его map-элементу). `instructions` — конкретное поручение участнику,
не копия системного prompt, всего backlog или методики скилла.

## Что получает роль

Системный агент задаёт полномочия и формат ответа; разрешённый скилл — методику.
Новый обычный input содержит отдельно workspace/унаследованные инструкции,
проверяемый snapshot и JSON `Task/context data`:

- **Orchestrator:** собственное поручение один раз, каталог ID/Beads ID/версий,
  зависимости, наблюдаемые состояния, решения и уточнения с источниками, последние
  результаты участников, актуальные `blocked`/ошибки, ссылки на пакеты и полную
  историю. `groupResults` отдельно сохраняет исход группы, `integrationError` и
  `integratedRevision` (если записаны): успешные children не подменяют результат
  их объединения. Полный групповой verdict с children доступен по `details`. Граф содержит только role/taskId/required, состав групп и переходы —
  без моделей, tools/skills и чужих `instructions`. Полных требований всех задач
  в карточках нет; они доступны по `details.path`. В прежних графах статусы отражают
  отчёты, а не доказательство проверки текущей версии. В [implements](implements.md)
  карточка taskId ссылается на реальный экземпляр и показывает состояние scheduler,
  включая ожидание зависимостей/слота/решения; индивидуальная готовность не заменяет
  проверку общего результата.
- **Worker:** точный собственный пакет, все его критерии, решения и ревизии до
  зафиксированной версии; локальное поручение/map-элемент/steer; относящиеся отчёты
  и замечания. Зависимости представлены ссылками на точные пакеты, не текстом
  остальных задач. Обычный отчёт другой задачи не пересылается; групповой
  результат фильтруется по taskId, сохраняя общий исход/ошибку интеграции.
  Непосредственное поручение manager и замечания проверяющего адресуются графом,
  независимо от taskId отправителя. Поручение manager передаётся точным summary
  с происхождением и ссылкой на полный исходный отчёт, без его backlog/конфигурации. Автор manager должен формулировать адресное поручение, а не
  копировать весь backlog в summary.
- **Reviewer:** те же точные требования и критерии своей задачи, текущая версия
  кандидата, ссылка и метаданные полного diff относительно начала workflow,
  прежние находки проверяющих со своими версиями. В directory-режиме diff не
  выдумывается. Разрешения остаются read-only, shell/правка тестов не предписываются.
- **Verifier:** собственный пакет и кандидат, критерии/сценарии из пакета и
  конкретного поручения, прежние находки. `otherReports` явно обозначены как чужие
  сообщения, **не собственная независимая проверка** этого посещения. Старые
  revision в отчётах не переименовываются в текущую. Непосредственный review,
  включая структурированные questions/findings, передаётся целиком и при отличии
  taskId reviewer от verifier (включая отсутствие привязки у verifier). Источник
  handoff содержит роль, задачу/версию отправителя, ревизию и разрешённую ссылку
  на точную запись history; одиноких неразрешимых reportVisit нет.

При отсутствии привязки пакет не угадывается. У непривязанного manager остаётся
каталог. Непривязанные worker/reviewer/verifier получают точный `definition.task`
как общие требования даже при наличии каталога пакетов. `taskScope.kind: workflow`
и пояснение явно обозначают отсутствие taskId; `sources.task`/requirementsPointer
ведут к `/definition/task`. Отдельные структурированные критерии не изобретаются:
verifier ссылается на существующие `/task/requirements` и `/assignment`, а не
на отсутствующий массив acceptanceCriteria. Чтобы ограничить такого участника
одной задачей вместо всего общего поручения, автор должен задать taskId.
Без `taskPackages` действует та же общая область: адресно разделить старый
монолитный текст DWF не умеет.
Исследовательские роли и planner этой сборкой не заменены.

## Сохранение и разрешённые ссылки

Посещение (включая child) хранит:

- `taskId/taskVersion` — прежняя привязка версии пакета;
- `taskContext` — структурированные данные, formatVersion 1, runId/inputId/role/node/participant,
  `candidate`, `assignment`, `sources` и ролевые поля;
- `prompt` — точный технический input, отдельно от данных;
- `contextDirectory` — приватный каталог сохранённых материалов данного inputId.

В `DWF_STATE_DIR/workflows/<runId>/contexts/<inputId>/` находятся `source.json`
(точное определение + исходные байты ввода), `<taskId>-v<version>.json` и
`history.json` (отчёты участников и групп, с полными исходными verdict).
Для группы children идут перед групповым результатом; номер reportVisit и
JSON pointer относятся к этому сохранённому history, не к живому UI.
Ссылки абсолютные, относятся к конкретному сохранённому input,
не к изменяемому текущему состоянию. `sources.task` и `requirementsPointer`
указывают точный источник требований; `sources.assignment` — узел исходного
определения. Решения сохраняют исходный `source`, уточнения — `steer:<id>`.
Данные не обрезаются по размеру и не заменяются автоматически сочинённой сводкой.
Повторная запись существующего документа допускается только с теми же байтами.
Подготовленный steer может добавить документ новой версии, не меняя старого.
Изменённый до admission group-child получает новый inputId и каталог; это
сохраняет исходный draft даже при interleaved результатах других implement.
После admission данные, prompt и разрешённый каталог заморожены; retry/restart
использует сохранённый input. Новой таблицы/миграции нет.

Runtime разрешает external_directory только для выделенного каталога contexts
данного запуска и имеющегося diff; произвольные URI пакета не расширяют разрешения.
При повторном входе в принадлежащую DWF сессию недостающий доступ к contexts
и при необходимости к новому diff/закреплённым материалам конфликта implement
добавляется без замены её остальных правил; grant общий для будущих input этого
запуска, а не новая запись на каждое посещение. `access: read`
означает разрешение при текущих tools, не доказательство существования файла.
Если `read` явно отключён, ссылка честно помечена unavailable. Проектные артефакты
разрешаются внутри workspace с проверкой traversal и symlink; абсолютные пути,
выходы наружу и неподдерживаемые схемы не авторизуются. HTTP(S) использует только
уже разрешённый webfetch. Будущий/недоступный материал не скачивается автоматически.

Это приватные runtime-файлы, не материалы для публикации. Устойчивость ссылок
действует пока сохранён каталог запуска на этой машине; перенос/удаление state,
прямое изменение файлов другим процессом и криптографическая защита — вне контракта.
Курсоры, acknowledgement и дельты реализованы в [контракте доставки xit.3](context-delivery.md).
`context.json` хранит полный текущий снимок; `taskContext`/UI taskData остаются
полными логическими данными, а точный prompt при повторном входе может содержать
только дельту относительно подтверждённого input той же сессии.

## UI и совместимость

UI читает `taskContext`, а не разбирает текст prompt. API вызова отдаёт отдельно
`taskData`, `taskSource` и `promptRaw`. Основной Task содержит точные требования
своей задачи или конкретное поручение управляющему; остальные поля раскрываются
в Structured task/context data, технический input — в Technical prompt.

Старая запись без taskContext имеет `taskSource: raw-only`, `taskData: null` и
подпись **Task (raw prompt only)**. Ей не приписываются восстановленные критерии,
роль/пакет из текста или якобы структурированная история. Сохранённые inputs не
пересобираются при restart. Ролевые скиллы не менялись: их текущие методики уже
соответствуют разделению обязанностей.

## Проверки и сравнение размера

```sh
node --test role-context.test.mjs task-packages.test.mjs ui.test.mjs
node --test --test-name-pattern='public CLI routes eight|public CLI task packages' acceptance/runtime.test.mjs
node acceptance/context-size.mjs
npm test
```

Корпус `acceptance/context-fixture.mjs`: восемь разных задач, 24 496 символов
исходных требований, 40 точных критериев, зависимости, решения с источниками.
Unit-проверки сопоставляют все поля каждого адресного пакета и отсутствие маркеров
полных требований семи остальных во всех трёх ролях. Проверяются также diff,
версии/источники, filtering handoff, запрещённые URI, UI raw-only и freeze.
Native-проверка запускает кандидатный `node ./dwf.mjs` с отдельным Git-проектом,
state/OpenCode-профилем и локальным HTTP provider: manager → восемь workers →
восемь reviewers → восемь verifiers → manager. Проверяются фактические wire-inputs,
отделение system, отсутствие shell/edit у reviewer и успешное native read по
внешней сохранённой ссылке каждого input. Модель управляемая: это проверка доставки
и разрешений, не оценка качества самостоятельной работы LLM. Отдельный CLI-тест
повторяет input после controller crash и позднего решения, не меняя его версию.

Воспроизводимое сравнение (UTF-16 code units, `.length`, не токены):

| Input | Прежняя сборка | Адресная сборка | Изменение |
| --- | ---: | ---: | ---: |
| Orchestrator | 57 440 | 7 852 | −86,3% |
| Worker | 29 700 | 5 044 | −83,0% |

Пути временных каталогов одинаковой длины; при иной среде размеры могут немного
измениться. System/skills исключены из обеих сторон: они передаются отдельным
агентом. Нет результатов в этом начальном посещении; после xit.3 ссылка на пустой
полный журнал есть также у worker (дополнительные 178 символов относительно
первоначального измерения xit.2).

Это **не повторное измерение частного исторического журнала 54k/29k**: его исходный
корпус здесь не предоставлен. Сравнение использует сопоставимые восемь полных задач
и прежний алгоритм сборки (сохранён в `context-size.mjs`). Старому workflow автор
передавал полное исходное task и свою задачу в worker.instructions, поскольку
прежняя сборка не читала пакеты; новая форма переносит эти же требования в пакет,
а в instructions оставляет только конкретное поручение. Поэтому manager прежде
получал каждый текст дважды (task + nodes), worker — свой дважды и остальные
семь по одному. Теперь manager получает ноль полных текстов и ссылки, worker —
только свой текст один раз, все пять критериев и решение без сокращения.
Собственное поручение manager повторялось дважды, теперь один раз.

Для контроля эффекта переноса instructions скрипт также считает старый алгоритм
на **неизменённом новом определении**: 31 152 символа manager и 26 422 worker.
Адресная сборка меньше и этой базы. Точные критерии и тексты не подгоняются под
лимит; сокращение достигается выбором данных и навигацией. Большие собственные
пакеты/поручения и отчёты могут давать большой контекст — произвольного clipping нет.


## Регрессии после ревью

Замечания о потере handoff, общей области непривязанных ролей и группового
результата воспроизведены новыми unit-тестами до исправления (8 содержательных
падений). Устранены причины: фильтрация по taskId больше не отбрасывает адресное
поручение/проверку, источник handoff разрешим; общий task явно определён;
история больше не заменяет группу только её детьми.

Дополнительные проверки через кандидатный CLI и изолированный native provider:

```sh
node --test --test-name-pattern='public CLI delivers|public CLI routes a real failed|public CLI prepared package' acceptance/runtime.test.mjs
```

- Четыре комбинации bound/unbound manager и verifier проверяют фактическую
  доставку уникального поручения, текста вопроса и structured questions. Чужой
  пакет manager и его дополнительный backlog не внедряются worker.
- Все три непривязанные роли получают точное общее требование с корректным scope.
- Два настоящих worker изменяют один файл несовместимо: их done сохраняются,
  реальная ошибка Git-интеграции доходит manager отдельно и читается native read
  из полного history. Родительское дерево остаётся без конфликтных изменений.
- Для настоящего prepared map-child CLI steer обновляет taskVersion и taskContext
  до версии 2; фактический wire prompt совпадает с сохранёнными данными. Второй
  steer после admission оставляет input версии 2 неизменным и доставляется
  отдельным посещением версии 3; соседний child остаётся на версии 1.

Это проверки доставки/исполнения DWF с управляемыми ответами, не выводы о качестве
решений живой модели и не механизм дельт.

### Повторная браузерная проверка с длинным TMPDIR

Замечание независимого verifier о `TIMEOUT` при открытии сессии воспроизведено
с `TMPDIR=/private/var/folders/0c/2cjdwzg1393b4h05f4ntjj180000gn/T/opencode`.
Причина — сопоставление сырого PTY-потока: native TUI разделяет искомую фразу
ANSI-позиционированием, отступами и вертикальной рамкой при переносе строки.
Оба PTY-сопоставления теперь используют `acceptance/pty-text.mjs`, игнорируя
только оформление (ANSI, пробельные символы, вертикальные рамки). Это проверка
наличия текста, не эмулятор экрана. Утверждения об ID/списке сессий, каталоге
и неизменности сообщений сохранены без изменений.

Четыре unit-регрессии покрывают ANSI внутри слов, CRLF/переносы, абсолютное
позиционирование native TUI и отрицательные совпадения. С тем же TMPDIR прошли
отдельный `node acceptance/ui-browser.mjs`, полный `npm run test:ui` и `npm test`
(275 Node-тестов, 12 Cucumber-сценариев). Проверки используют изолированный
управляемый provider, а не оценивают качество решений живой модели.

## Документы из результата участника

Поле JSON-результата `artifacts` — массив относительных путей (до 16 UTF-8 файлов
по 1 MiB). DWF сохраняет неизменяемые копии в каталоге контекста попытки; Git-файлы
читаются из отчётной ревизии, включая ещё не интегрированные предложения. Отчёт
содержит ссылки с inputId, revision, sha256 и путём обычного текстового файла. Недоступность
сохраняется явно. Получатели имеют прежний доступ только к контекстам DWF,
а не ко всем рабочим деревьям. Упоминание пути в свободном тексте доступа не даёт.
