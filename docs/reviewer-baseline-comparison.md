# Проверка утверждений о поведении исходной версии

В независимой пробе more-itertools reviewer потребовал восстановить продолжение
того же чанка после исключения, приписав эту возможность исходной реализации.
Проверка на Python 3.9.6 и 3.14.6 показала, что исходный чанк также завершается.
Worker выполнил дополнительную переработку по этому замечанию.

Новая инструкция требует обосновать поведение исходной версии на том же входе.
Для библиотечного поведения основанием служат доступная реализация, документация
или выполненная проверка. Неустановленное поведение оформляется конкретным
вопросом для verifier. Передача необходимой проверки вместе с `approve`
допускается только перед непосредственно следующим обязательным verifier.
В остальных графах необходимая невыполненная проверка приводит к `blocked`.
Доказанный дефект и явное невыполненное требование
по-прежнему требуют `changes`.

## Условия

Использована замороженная ревизия `b94a9d5` и модель
`openai/gpt-6.1-sol-ultrafast` с reasoning `high`. У каждой попытки собственные
native-сессия, сервис, проект и состояние. В паре совпадают исходники, diff,
задание, инструменты и скилл `code-review`. Меняется одна инструкция reviewer.
Порядок вариантов чередуется между повторами.

Выполнены 60 обзоров десяти случаев, по три повтора на вариант. После каждого
`approve` запускался новый штатный verifier с исходным заданием, теми же файлами
и полученным замечанием reviewer. Всего выполнены 27 таких проверок. `changes`
завершает оцениваемый путь решением о необходимости исправления.

Проверены фактические native-модели, reasoning, хеши входов, границы доступа,
завершение сессий и отсутствие ожидающих сообщений. У verifier также проверены
вызовы команд и неизменность проекта. Сырые ответы, команды, код корпуса,
квалификация и журналы сохранены в закрытом проверяющем контуре.

## Разметка и контрольные случаи

Девять случаев вошли в основную оценку.

- Эквивалентная обёртка `islice` в ограниченном контракте обычного итератора.
- Потеря продолжения у обёрток `chain` и `map`.
- Явное новое требование продолжения после ошибки.
- Обработка JSON и клонирование свойств объекта по заданному контракту.
- Потеря допустимых значений при удалении `null`.
- Два новых отложенных случая с собственным `Cursor` и фильтрацией положительных ID.

Полный пример `ichunked` исключён из основной метрики после проверки verifier.
Его исходная метка `approve` оказалась слишком сильной для расширенного
контракта после ошибки. Verifier воспроизвёл другие различия в сохранённых
чанках и последующем чтении внешнего итератора. Эти различия также есть
в принятом upstream-эталоне. В исходной OSS-приёмке проверялась передача
исключений, а продолжение после ошибки отдельной гарантией не выделялось.
Все шесть ответов этого случая и три проверки verifier сохранены отдельно.
Задания и первоначальные метки завершённой серии не переписывались.

Для клонирования `Object.assign` и `Object.fromEntries` различаются при
собственном перечислимом свойстве `__proto__`. Вариант `Object.fromEntries`
выполняет заданное требование переноса ключей и значений, поэтому метка
`approve` сохраняется. Полная эквивалентность реализаций не утверждается.

Два предшествующих пилота также сохранены отдельно. В первом минимальный пример
менял момент вызова `iter()`. Во втором широкий контракт обёртки включал
сохранение подкласса и значения `StopIteration`, которое новая реализация
теряла. Эти случаи не используются для заявления об улучшении.

## Независимый аудит первого варианта

Хеш испытанного поля DWF `agent.system` первого варианта равен
`dad00f79034a9a8ed3ed002b0242f5e307927ce832c905997cd85db51eadc7f4`.
Native runtime может добавлять собственный системный контекст.
Полный `npm test` прошёл 30 проверок контура, 62 проверки продукта,
12 Cucumber-сценариев из 116 шагов и 21 native-проверку.

Независимый аудит отклонил первый вариант. В графах reviewer-only и
verifier→reviewer вопрос после `approve` мог остаться без исполнения.
Существующая проверка актуальности одобрений не проверяет порядок этих ролей.
Приведённая серия отражает только исследовательский путь reviewer→verifier.
У самого reviewer обнаружение настоящих дефектов составило 15/15 для исходной
инструкции и 13/15 для первого варианта. После verifier результат был 15/15
для обоих вариантов.

Исправленный кандидат получает контекст фактического перехода. Необходимый
вопрос допускается с `approve` только перед непосредственно следующим
обязательным verifier. Для остальных маршрутов действует `blocked`.
Групповые переходы оцениваются консервативно. Этому кандидату требуется
отдельная проверка, проведённая в следующей серии. Результаты первой серии
не подтверждают его приёмку.

## Повторное сравнение с учётом маршрута

В серии V5 заранее зафиксированы 11 случаев, по три повтора двух вариантов.
Девять случаев перенесены из исследовательской серии, два новых отложенных
случая проверяют `enumerate` и копирование `Map`. Полный пример `ichunked`
исключён до начала этой серии. Все случаи квалифицированы на Python 3.9.6
и 3.14.6, проверки JavaScript выполнены на Node 26.8.1.

Испытывался код `2610b29`. Обе стороны получили одинаковый контекст
непосредственно следующего обязательного verifier. Исходные инструкции взяты
из `20cd01d`. Модель, reasoning, инструменты, скиллы и входные файлы совпадали.
После каждого `approve` запускался свежий штатный verifier. Всего выполнены
66 обзоров и 37 проверок. Первичные записи 103 сессий подтверждают 610 сообщений
модели, конфигурации агентов, учёт токенов, окончание работы и пустые inbox.

Новая инструкция передала девять настоящих дефектов verifier вместо
самостоятельного утверждения о библиотечном поведении. Все девять подтвердились
выполнением кода. Уменьшение числа ложных требований сопровождалось увеличением
числа обращений, токенов и времени. Сумма длительностей учитывает параллельные
обращения отдельно. Денежная стоимость и полный цикл доработок worker
не оценивались. Подробности сохранены в
[машинной сводке V5](../acceptance/reviewer-context-results.json).

Ещё 27 native-вызовов reviewer проверили контексты reviewer-only,
verifier→reviewer и группового перехода. Использованы два дефектных случая и
один исправный, по три повтора. Получены восемь `changes`, десять `blocked`
и девять `approve`. Все дефектные случаи остановлены, исправный контроль
одобрен во всех повторах. Это проверка входных контекстов роли. Предыдущий
результат verifier в одном контексте задан контролируемым входом, эти вызовы
не являются 27 полными CLI-workflow.

Перед V5 остановлен пилот V4, поскольку полный архив движка содержал сводку
предыдущих ответов. Его результаты сохранены отдельно. V5 предоставляет
только необходимые файлы движка и скиллы. Проверки перед допуском обращаются
к существующим закрытым файлам и требуют `EPERM`. Для исторических записей
V3 отдельно повторены проверки доступа с существующим файлом корпуса.

В текущем коде хеш DWF `agent.system` reviewer равен
`28601000dab18bb9dc7ba7159cf3b5044142f0a880e8cc5933db9dd08d24f0c4`.
Полный `npm test` для `9c36fe2` прошёл 31 проверку контура, 63 проверки продукта,
12 Cucumber-сценариев из 116 шагов и 21 native-проверку.

Независимый аудит `a7751c8` одобрил код и приведённые ограниченные выводы.
Проверяющий пересчитал все 130 вызовов V5 и маршрутизации по первичным записям,
повторил 37 содержательных проверок verifier и семь собственных CLI-сценариев.
Он также проверил шесть новых OSS-кандидатов и подтвердил сводку из 20 попыток
с 12 чистыми принятыми результатами.

Во время аудита организатор добавил материалы внутрь проверяемого каталога.
Защита снимка потребовала повторной проверки. Окончательный снимок получил
новые одобрения reviewer и verifier. Независимый полный набор тестов прошёл
во внешней копии. В последнем проходе инструмент ограничил повторный запуск
из этой копии, поэтому применимость результата подтверждена побайтным
равенством всех 55 отслеживаемых файлов. Исходные и повторные события сохранены.
