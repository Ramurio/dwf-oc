# Скиллы и проверки проекта

[README](../README.md) · [Установка](install.md) · [Справка workflow](workflow.md)

## Скиллы участников

Worker получает `code-work` из `skills/worker/`. Он объединяет проверку
изменяемого поведения, диагностику сбоев и проектирование интерфейсов.
Reviewer получает `code-review` из `skills/reviewer/`. Он сверяет изменения
с поручением, проверяет корректность, сохранность данных, ожидаемую нагрузку,
качество тестов и обоснованность структуры. Обязательные исправления должны
иметь конкретное обоснование. Повторное ревью проверяет устранение замечаний
и регрессии от исправлений.

Verifier получает `code-verify` и выполняет независимые проверки поведения.
Orchestrator получает `workflow-orchestration`: методику выбора задач по зависимостям,
разбора замечаний и проверки совместимости результатов. Системный промпт отдельно
задаёт контракт решений: выбор именованного перехода, поручение адресату в summary,
запрет самостоятельной интеграции и условия done/blocked. История и актуальные
требования к одобрениям приходят в контексте вызова. Старый `workflow-summary`
остаётся доступен для явно заданных настроек и сохранённых агентов. Служебный planner
одноагентного сценария получает `task-planning` для текстового плана.
Его единственный инструмент — загрузка этого скилла.
Исследовательские роли и их скиллы описаны в [research-mid](research-mid.md).

Исходники общих скиллов поддерживаются в отдельном репозитории
[ramu-skills](https://github.com/Ramurio/ramu-skills). DWF содержит копии
в `skills/<роль>/<имя>/SKILL.md`. Запуск не зависит от соседнего проекта.
После согласованной правки исходника обновляй копию той же версией.
OpenCode показывает краткое описание и загружает содержимое по вызову `skill`.

Каждое посещение reviewer в Git-workflow получает путь и размер полного diff
от исходной ревизии workflow до проверяемого Git tree. Файл включает
незакоммиченные изменения и хранится отдельно от рабочего дерева. После
доработки создаётся новый файл, предыдущие материалы сохраняются.
Большие diff читаются частями.

Адаптации используют требования и соглашения текущего проекта. Управление
переходами, сессиями и Git остаётся у DWF. Источники скиллов указаны в README
репозитория `ramu-skills`. Автор адаптаций — Ramurio.
Лицензия находится в [skills/LICENSE](../skills/LICENSE).
Системные промпты DWF написаны на английском. Профиль хранит версии промптов
и содержимого скиллов отдельно. Обновление скилла сохраняет доступ к версии
прежней сессии.

## Проверки

Выполняй команды из каталога установленного DWF.

```sh
npm test
npm run test:steps
DWF_TEST_REAL_STATE_DIR=/absolute/path/to/authorized-dwf-state \
DWF_PLANNER_MODEL='{"provider":"openai","modelId":"gpt-6.1-sol"}' \
npm run test:real
```

`npm test` исполняет самопроверки, тесты хранения и Git-интеграции, controlled-сценарий,
сценарии восстановления, продолжения по длине, параллельных запусков и циклов
reviewer/verifier с сохранением сессий, затем native-проверки OpenCode.
`test:steps` проверяет только привязку шагов.

Управляемые проверки используют локальную модель без секретов. Для `test:real`
нужен отдельный авторизованный профиль с остановленным сервисом. Приёмка сама
запускает его, сохраняет штатный модельный транспорт, добавляет временный
нативный наблюдатель OpenCode, проверяет результат после остановки и удаляет
наблюдатель. В отчёты попадают параметры модели и текст ответа.
Заголовки авторизации и токены туда не пишутся.

Отчёты создаются в `acceptance-results/opencode/`. Каталог исключён из Git.
Сводки завершённых серий находятся в `acceptance/`, оговорки прежних прогонов
сохранены в [истории испытаний](development-history.md#отчёты-итераций-opencode).

## Независимый тестер

Запускатель создаёт свежую сессию обычного OpenCode build, загружает только каталог
скилла `dwf-oc` и передаёт содержимое файла как пользовательское поручение.
Тестер сам составляет workflow и запускает публичный `dwf`. Для каждой пробы
создаётся отдельная Git-копия чистой исходной ревизии, в которую DWF затем
интегрирует результат. Исходный стенд сохраняется для повторения той же задачи.

```sh
node acceptance/tester.mjs start --project /path/to/project --prompt-file /absolute/path/to/task.txt
node acceptance/tester.mjs inspect /path/printed/as/attempt --watch
```

`start` печатает путь пробы и наблюдает до итогового ответа. Если наблюдение
оборвалось, `inspect --watch` подключается к сохранённой сессии с тем же ID ввода.
Без `--watch` он возвращает текущее состояние. Завершение сессии тестера ещё
требует проверки его отчёта и фактического состояния запущенного им workflow.

По умолчанию пробы находятся в `~/.dwf/tester/attempts/`. `DWF_STATE_DIR` задаёт
другой корень DWF. В каждой пробе сохраняются `attempt.json`, `prompt.txt`,
`skills.json`, видимые сообщения и вызовы инструментов в `messages.json`,
`state.json` и окончательный `report.md`. Личная цепочка рассуждений исключается
из журнала. Тестер использует GPT-6.1 Sol Ultrafast с reasoning high.

Тестер использует общий пользовательский сервис и вход OpenCode. Он получает
свежую сессию с доступом к управляющему скиллу `dwf-oc`. Участники его workflow
работают в том же сервисе. Для испытаний с закрытым эталоном ниже выделяется
временный профиль внутри тестового стенда.

## Изолированные испытания с закрытым эталоном

`node acceptance/benchmark.mjs /private/path/case.json` запускает пробу
с проверкой границ macOS sandbox-exec. Файл настройки находится в контуре
проверяющего и задаёт `root`, `project`, `baseline`, `prompt`. Необязательные
поля включают `runtimeRevision`, `readable`, `copy`, `environment`, `hidden`.

```json
{
  "root": "/private/evaluation/series",
  "project": "/private/evaluation/upstream",
  "baseline": "commit-before-the-change",
  "prompt": "Реализуй описанное поведение через DWF.",
  "readable": ["/private/evaluation/toolchain"],
  "environment": {"GOCACHE": "{{attempt}}/go-cache"},
  "hidden": ["/private/evaluation/hidden-check.txt"]
}
```

Каждая проба получает один исходный Git-коммит, отдельные каталоги состояния
и зафиксированную копию исполняемого DWF и скилла. История исходного репозитория,
записи задач DWF и материалы прошлых проб остаются за границей доступа.
`copy` принимает массив объектов `from` и `to`, где `to` относителен каталогу
пробы. Так можно подготовить автономный кеш объявленных зависимостей.
Сетевые запросы модели проходят через прокси с ограниченным списком адресов.
Доступ к другим адресам и к соседнему локальному сервису проверяется перед
запуском. `hidden` перечисляет существующие файлы, чтение которых должно
отклоняться. Проверка границ, происхождение исходников, версии и журналы
сохраняются в закрытом `root`. Приёмку готового результата выполняют отдельно.
