# Workflow и CLI

[README](../README.md) · [Установка](install.md) · [Скиллы и проверки](development.md)

## Обычная разработка

Сначала выполни [установку](install.md), включая регистрацию команд в PATH,
управляющий скилл и авторизацию. Запускай CLI из целевого проекта.

```sh
dwf schema
dwf start --file /absolute/path/to/workflow.json
dwf inspect <runId>
dwf continue <runId>
dwf inspect <runId> --watch
```

Схему сохрани вне проекта. В `task` запиши поручение и критерии готовности.
`entry` задаёт первый узел. `nodes` описывает участников, `transitions` задаёт
переходы по результатам. Переход `null` завершает процесс.
Необязательные `instructions` задают особую область работы участника.
Роли получают системные инструкции, скиллы и формат результата от DWF.

Пример разработки с возвратом замечаний и локальным merge использует
GPT-6.1 Sol с reasoning high и обычной скоростью.

```json
{
  "task": "Реализовать поручение пользователя и проверить критерии готовности",
  "entry": "work",
  "merge": true,
  "roles": {
    "worker": {"model": {"provider": "openai", "modelId": "gpt-6.1-sol"}, "reasoning": "high"},
    "reviewer": {"model": {"provider": "openai", "modelId": "gpt-6.1-sol"}, "reasoning": "high"},
    "verifier": {"model": {"provider": "openai", "modelId": "gpt-6.1-sol"}, "reasoning": "high"}
  },
  "nodes": {
    "work": {"role": "worker"},
    "review": {"role": "reviewer"},
    "verify": {"role": "verifier"}
  },
  "transitions": {
    "work": {"done": "review"},
    "review": {"approve": "verify", "changes": "work"},
    "verify": {"approve": null, "changes": "work"}
  }
}
```

Результат worker — `done`, reviewer и verifier — `approve` или `changes`.
Orchestrator выбирает `done` либо именованное решение из своих `transitions`.
Участник может вернуть `blocked`, если продолжение невозможно. По умолчанию
это останавливает запуск. Для worker, reviewer и verifier можно задать явный
переход `blocked` к orchestrator: он получит препятствие и выберет следующий шаг.
Его собственный `blocked` всегда останавливает процесс для внешнего решения.

## Пакеты задач

Необязательные `taskPackages` хранят точные требования, критерии, зависимости,
решения и артефакты отдельно от инструкций роли/скилла. `nodes.<node>.taskId`
связывает участника с пакетом; посещение фиксирует его ID и версию.
Формат, аудит исходного ввода, версионированный steer и точки подключения
контекста/runtime/UI описаны в [едином контракте](task-packages.md).
Обычные роли получают [адресный контекст](role-context.md) по привязанному пакету;
сам по себе пакет не меняет плоский граф. В `implements` те же ссылки зависимостей
управляют реальной очередью задач (см. ниже).

## Параллельные implement

Для первоклассных независимых циклов задач используй секцию `implements` с явным
`concurrency`, taskId и ролями worker/reviewer/verifier. Orchestrator выдаёт
конкретные поручения и разрешает объединение; DWF сохраняет отдельные worktree,
сессии, очереди и результаты. Индивидуальные проверки не заменяют проверки общего
дерева. [Схема, события, восстановление и UI-контракт](implements.md),
[полный пример](../workflows/parallel-implement.json). Старые `groups` не меняются.

## Управление несколькими задачами в прежнем плоском графе

Orchestrator — отдельный управляющий узел общего графа. Его дополнительные
исходы имеют произвольные имена в формате идентификаторов узлов и ведут к
существующим участникам или группам. `blocked` зарезервирован для остановки;
только `done` может вести в `null`. Например:

```json
{
  "task": "Реализовать задачу и проверить совместимость результата",
  "entry": "manager",
  "merge": true,
  "nodes": {
    "manager": {"role": "orchestrator"},
    "work": {"role": "worker"},
    "review": {"role": "reviewer"},
    "verify": {"role": "verifier"}
  },
  "transitions": {
    "manager": {"implement": "work", "recheck": "review", "done": null},
    "work": {"done": "review"},
    "review": {"approve": "verify", "changes": "work"},
    "verify": {"approve": "manager", "changes": "work", "blocked": "manager"}
  }
}
```

Решение `{"outcome":"implement","summary":"Причина и конкретное поручение"}`
сохраняется как результат посещения manager. DWF передаёт его worker, выполняет
выбранный переход и сохраняет сессию при повторном входе. Неизвестный исход
останавливает запуск. Orchestrator получает граф, историю и список недостающих
одобрений текущей ревизии. `done` не заменяет обязательных проверок перед merge.

Для нескольких задач прочитай `dwf preset show implement`, перенеси его узлы
и переходы в общий граф с отдельным префиксом для каждой задачи. Сохрани настройки
участников и циклы исправлений; задай каждому его часть требований из Beads.
Успешный verifier возвращает к manager. Добавь manager маршруты к worker и
reviewer каждой задачи, чтобы он мог назначать доработку и повторные проверки.
Один workflow имеет один режим merge; интеграцию выполняет контроллер в конце.
Проверяющие каждой задачи остаются обязательными: после поздних изменений
manager должен получить их одобрения итогового общего снимка.

Обычные маршруты последовательны и работают над общим рабочим деревом; это
не параллельные дочерние workflow. Для одношагового параллелизма остаются группы; для циклов задач — `implements`.
Управляющий orchestrator не может быть членом группы: её участники возвращают
результаты группе, а не исполняют собственные переходы. Все объявленные маршруты
видны в UI ещё до первого обращения к участнику. Состав графа задаётся при запуске.

DWF создаёт отдельную ветку и рабочее дерево из чистой исходной Git-ветки.
Путь рабочего дерева возвращает `inspect`. При `merge: true` исходная ветка
должна оставаться чистой и на прежнем коммите до интеграции.
Без `merge: true` автоматическое слияние не выполняется.

## Настройки участников

Настройки в `roles` наследуются узлами соответствующей роли. Узел может
переопределить `model`, `reasoning`, `tools`, `skills` и `memory`. Списки
заменяются целиком. Пустой список отключает инструменты или скиллы.
`reasoning: null` отключает выбор варианта модели. `memory: false` создаёт
новую сессию при следующем обычном посещении. По умолчанию история обычных
ролей сохраняется. У исследовательского комитета отдельная политика сессий,
описанная в [research-mid](research-mid.md).
Выбранная конфигурация и версии системных инструкций сохраняются с запуском.

`workspace: "directory"` использует текущий каталог для read-only ролей,
в том числе вне Git. Снимок файлов контролирует их сохранность. Этот режим
не поддерживает worker и merge. По умолчанию используется `worktree`.

```json
{
  "task": "Проанализировать документы проекта",
  "workspace": "directory",
  "entry": "review",
  "roles": {
    "reviewer": {
      "model": {"provider": "openai", "modelId": "gpt-6.1-sol"},
      "reasoning": "high",
      "tools": ["read", "glob", "grep"],
      "skills": []
    }
  },
  "nodes": {"review": {"role": "reviewer", "memory": true}},
  "transitions": {"review": {"approve": null, "changes": null}}
}
```

Завершение требует актуального одобрения каждого обязательного reviewer
и verifier. Они обязательны по умолчанию. `required: false` делает конкретного
проверяющего консультативным. Отрицательный итог обязательной проверки
препятствует успешному завершению и при `merge: false`.
Для `merge: true` нужны обе роли и их фактические одобрения текущей версии.

## Уточнения и остановка

```sh
dwf steer <runId> <node> --message-file /absolute/path/to/refinement.txt
dwf stop <runId>
```

Уточнение доставляется на границе ответа. Уточнения доставляются по одному
в порядке приёма. Если первое ожидающее уточнение адресовано участнику
подготовленной группы до начала её запуска, оно дополняет это посещение
и сохраняет его сессию. При `memory: false` эта сессия может быть новой.
Группа выполняется полностью. Остальные ожидающие уточнения и команды,
поступившие после начала группы, доставляются отдельными посещениями
с последней сессией адресата, если она есть. Когда очередь пуста, маршрут
задают переходы последнего посещения группы либо отдельного узла.
Если уточнение отменяет подготовленную группу, уже принятые уточнения её
map-участникам сохраняют адресата и данные элемента после восстановления контроллера.

В цепочке `worker → reviewer → verifier → summary` уточнение текущему worker
сохраняет обе проверки. Ранний вызов verifier продолжит путь `verifier → summary`.
Отсутствие актуального одобрения обязательного reviewer приведёт к `failed`.
Выбирая участника, сохраняй путь через необходимые проверки.

Остановка прерывает сессии и команды запуска, сохраняет историю и возвращает
`cancelled`. Повторная остановка возвращает то же состояние. Приём команд
и переход к завершению сериализованы, поэтому принятое уточнение или остановка
учитываются до интеграции.

Интерактивный `attach` ещё не реализован. Договорённости о терминальном чате
сохранены в [истории](development-history.md#видение-и-решения-интервью).
Для ручной работы запускай `opencode` из каталога нужного проекта.

## Параллельные группы

В `groups` можно задать `{"members":["first","second"]}` для одновременного
запуска существующих узлов. Группа имеет переходы `done`, `changes`, `failed`
и передаёт следующему узлу все результаты с идентификаторами источников.
Ошибки ветвей сохраняются. `required` задаёт обязательное подмножество участников,
по умолчанию обязательны все.

Форма `{"member":"worker","itemsFrom":"planner"}` создаёт участников по
массиву `items` из результата указанного узла. Также можно задать `items` прямо
в группе. Элементы имеют уникальные `id`, отдельные сессии и адреса
`groupName/itemId` для steering. Результаты уже завершённых ветвей используются
при восстановлении контроллера.

Писатели получают отдельные рабочие деревья. Успешные изменения объединяются
перед следующим узлом. Конфликт сохраняет исходное дерево группы и результаты
ветвей. Общее ревью и верификацию размещай после объединения. Пример полного
графа находится в `references/cli.md` управляющего скилла `dwf-oc`.

## Пресеты

Попроси агента «сохрани этот workflow как “Разработка с ревью”».
Агент сохранит схему выбранного запуска по его `runId`.
Позже можно сказать «запусти DWF “Разработка с ревью”» и дать новое поручение.

```sh
dwf preset save "Разработка с ревью" --from-run <runId>
dwf preset list
dwf start --preset "Разработка с ревью" --task-file /absolute/path/to/new-task.txt
```

Сохраняются состав и инструкции участников, их фактические модели, глубина
рассуждений, инструменты, скиллы, настройка памяти, группы и переходы,
режим рабочего каталога и настройка слияния. Новый запуск использует текущий
проект, новое поручение из `--task-file` и новые сессии участников.
Пресеты доступны в разных проектах через общий каталог состояния DWF.
Русские имена и имена с пробелами передавай в кавычках.
Повторное сохранение под тем же именем обновляет пресет.

Команда `dwf preset save my-workflow --file /absolute/path/to/workflow.json`
сохраняет схему из файла. Схема исследования `research-mid` поставляется
в `workflows/`. Её нужно [зарегистрировать перед запуском](research-mid.md).

Старый формат `{"planner":{"task":"поручение"}}` продолжает работать.

## Состояние и наблюдение

`start` возвращает JSON с `runId`. Для workflow перед этим сохраняются состояние
и запуск контроллера. В одноагентном формате ожидается принятие поручения OpenCode.
`inspect` возвращает `status` со значением `running`, `succeeded`, `failed`
или `cancelled`. Успешный итог содержит `result`, ошибка содержит причину в `error`.
Остановка даёт `cancelled`.

`blocked` — значение `outcome` участника. При таком ответе последовательного
участника без ожидающих команд workflow завершается с `status: "failed"`.
Причина записывается в `error`.

Для workflow доступны `current`, `history`, `workspace` и итоговый `result.commit`
после merge. Для старого планнера `result` содержит точный текст.
Недоступность сервиса сообщается отдельным полем `service` и сама по себе
не превращает поручение в окончательно неудачное.

`dwf inspect <runId> --watch` выдаёт события отдельными JSON-строками. Первое
и последнее события имеют `type: "snapshot"` и полное состояние в поле `state`.
Между ними события `type: "update"` передают изменившиеся поля в `changes`.
`removed` перечисляет удалённые поля. `historyUpdates` заменяет или добавляет
изменившиеся посещения по нулевому `index`, передавая запись в `entry`.
Неизменившиеся отчёты этапов повторно не передаются.
Закрытие наблюдателя сохраняет независимое исполнение workflow.

`current.startedAt` показывает начало этапа, `current.progress.updatedAt`
показывает последнюю активность в Unix ms. Прогресс содержит видимое промежуточное
`message`, последние `tools` с их состояниями и сведения о штатном повторе
запроса `retry`, когда они доступны. Он сохраняется в SQLite и доступен
при повторном подключении.

После merge `result.integration` подтверждает состояние `merged`, ветку и коммит.
Итоговый `summary` начинается с фактического результата интеграции DWF, после
которого идёт отчёт участника, подготовленный до слияния. Это отображение
применяется и к ранее завершённым workflow.

При одобрении Git-изменений verifier начинает `summary` с заголовка
`DWF <type>: <описание>`, например `DWF fix: preserve admission input on retry`.
Он выбирает тип по смыслу изменения и описывает конкретный результат.
Используются типы [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) — `feat`, `fix`, `refactor`, `perf`,
`docs`, `test`, `build`, `ci`, `style`, `chore`, `revert`. Допустимы scope и `!`
для несовместимого изменения. После пустой строки идёт отчёт о проверке.
DWF берёт заголовок у последнего обязательного verifier, одобрившего текущий
снимок, даже если workflow завершается через orchestrator. Для старых ответов
без такого заголовка используется `DWF chore: ` и первая строка поручения
длиной до 100 символов.

Родительские `AGENTS.md` исходного проекта сохраняются при запуске и передаются
участникам вместе с путём рабочего дерева. Инструкции внутри проекта участники
читают из рабочего дерева. Вычислением снимков и соответствием одобрений
текущим файлам управляет DWF.

Сохранённый окончательный результат доступен без работающего OpenCode.
Для уточнения незавершённого состояния `inspect` при необходимости поднимает
общий сервис. Его запуск может возобновить другие незавершённые поручения
согласно штатной ограниченной политике OpenCode. Обрывы по длине также
обрабатываются штатно. После успешного продолжения текст всех частей читается
в исходном порядке. Аварийно остановленный контроллер workflow восстанавливается
через `inspect` после истечения его 30-секундной аренды.

После терминальной ошибки используйте `dwf continue <runId>`: [проверяемые границы, явные решения и история восстановления](continuation.md). `cancelled` требует `--resume-cancelled`; неизвестные внешние действия требуют решения, а не ручной правки SQLite.

## Настройки и хранение

| Настройка | Назначение |
| --- | --- |
| `DWF_STATE_DIR` | Абсолютный корень состояния вне рабочего проекта, по умолчанию `~/.dwf` |
| `DWF_PLANNER_MODEL` | JSON с `provider` и `modelId`, fallback обычных ролей — `openai/gpt-6.1-sol-ultrafast` |
| `DWF_PLANNER_REASONING` | Уровень рассуждения по умолчанию — `high` |
| `OPENCODE_CONFIG` / `OPENCODE_CONFIG_CONTENT` | Штатная конфигурация общего сервиса OpenCode |

Для обычной скорости явно задавай `openai/gpt-6.1-sol` в `roles` или узлах.
Исследовательские роли имеют собственные значения модели по умолчанию.

DWF использует OpenCode 2.2.5. Отдельный контроллер ведёт переходы,
OpenCode исполняет роли. Связи запусков, пресеты и принятые результаты находятся
в `<state>/dwf.sqlite`. Рабочие деревья находятся в `<state>/workflows/`.
Пользовательская команда `opencode` и DWF подключаются к одному native-сервису.
Общий профиль хранит вход, модели и сессии. По умолчанию его регистрация находится
в `~/.local/state/opencode/service.json`, конфигурация в `~/.config/opencode`,
native БД в `~/.local/share/opencode/`. Блокировка запуска DWF находится рядом
с регистрацией в `dwf/`. `DWF_STATE_DIR` сохраняет этот профиль при смене каталога
запусков. Новый workflow запоминает пути профиля для восстановления контроллера.
Старые workflow завершаются на своей прежней базе. Несовместимая версия сервиса
требует явного обновления.

Вход выполняется один раз через `opencode auth login`.
[Ручной login и проверка](install.md#5-авторизовать-участников-dwf)
описаны в основной инструкции установки. Учётные данные не входят в примеры.
