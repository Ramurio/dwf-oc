## Снимок и дельта

`prepareRoleInput` по-прежнему собирает точный актуальный ролевой снимок
`visit.taskContext`. Требования, критерии и решения не пересказываются и не
обрезаются. `context.json` сохраняет этот снимок рядом с `source.json`, пакетами
и `history.json`. Все роли получают ссылку `history` на полный журнал, включая
children и исходы интеграции групп. Данные других задач по-прежнему адресуются
по правилам xit.2, а не внедряются в собственные требования.

Первое обращение получает снимок inline. Следующее обращение в **ту же сессию
того же участника** получает `Task/context data` с:

- `delivery.mode: "delta"`, `baseInputId` подтверждённого предыдущего input;
- `delivery.snapshot` — разрешённая ссылка на полный актуальный `context.json`;
- `delivery.history` — полный журнал;
- `updates` — упорядоченные операции JSON Patch (`add`, `remove`, `replace`,
  `move`, пути JSON Pointer) относительно прежнего **полного** taskContext;
- идентичностью input/роли/участника, кандидатом и идентичностью implement.

Неизменившиеся требования и решения остаются в силе. Пустое/отсутствующее поле
в дельте не означает их отмену; удаление задаётся явной операцией `remove`.
Массивы каталогов, результатов и событий сравниваются по элементам; известные
идентичности позволяют перемещать старые записи, не пересылая их текст заново.
Новые решения сохраняют исходный `source`, новые отчёты — исходный input/revision.
Для непривязанных/старых workflow `userInputs` сохраняет точные принятые steer
с адресатом, `steer:<id>` и статусом команды. Новые команды сохраняют явный
`revisionKind`; старым без него классификация не приписывается. Поэтому recovery
и memory:false не теряют прежние уточнения даже без журнала пакетных ревизий.
Manager видит эти входы всех адресатов, worker — только свои. Пакетные ревизии
не дублируются в этом поле. Статус команды не доказывает прочтение моделью.
Неизменные инструкции manager и накопленные находки не дописываются заново.
Полные новые данные могут быть большими: лимита или автоматической сводки нет.

Если прежний контекст утрачен (например, восстановление сессии или compaction),
сам input явно требует сначала прочитать полный **актуальный** snapshot. Его
ссылки ведут к точным требованиям/решениям и полному журналу, а не к цепочке
обязательных для replay дельт. Разрешение contexts добавляется прежним механизмом
native admission, в том числе при создании утраченной сессии. Если `read` запрещён,
DWF консервативно отправляет актуальный снимок inline вместо дельты: недоступный
fallback не выдаётся за достаточный контекст.

Новая sessionId, `memory:false`, другой scoped participant/implement или отсутствие
подтверждённого delivery у старой записи тоже означают inline-снимок. Сохранённые
raw-only inputs не реконструируются и не меняются. Прежняя семантика steering,
включая повторное использование установленной сессии при `memory:false`, сохранена;
такое обращение всё равно получает полный текущий снимок.

Это сокращает **новые inputs DWF**, а не удаляет native-историю OpenCode и не
обещает сокращения всего HTTP model request на тот же процент. Native-сервис
сам передаёт модели прежние сообщения и управляет compaction.

## Устойчивая граница

В прежнем SQLite JSON `workflows.state`, без таблицы/миграции, каждый новый
обычный visit или group-child хранит:

```json
{"delivery":{"formatVersion":1,"mode":"delta","baseInputId":"msg_previous",
 "acknowledged":false,"snapshot":{"path":".../context.json","access":"read"}}}
```

Курсор — последний подтверждённый delivery в сохранённых visits **с теми же
sessionId, participant и implementId**; отдельного изменяемого глобального cursor
нет. `taskVersion` и implement event sequence не являются этим курсором.

1. **Prepared:** снимок, ссылки, prompt и inputId сохранены. Курсор не продвинут.
   Отменённый draft ничего не «прочитывает». Изменяемый group-child получает
   отдельный inputId/каталог, не переписывая старые материалы. Это относится
   и к raw-only legacy draft: после аварии до SQLite commit у него уже могут
   существовать orphan-документы, хотя taskContext ещё не записан в state.
2. **Admission started:** прежняя сохраняемая граница замораживает input до send.
   Prompt, snapshot, base и sessionId после неё неизменяемы.
3. **Acknowledged:** только успешный native inbox admission устанавливает
   `admitted` и `delivery.acknowledged` вместе, под **существующей** транзакцией
   и fencing владельца. Это подтверждение приёма inbox, не доказательство чтения,
   понимания или отдельного HTTP-вызова модели.

При потере ответа/аварии до сохранения acknowledgement повторяются тот же
sessionId, inputId и точные байты prompt. Никакой новой попытки или пересборки
по поздним решениям нет; native inbox дедуплицирует повтор. Поздние сведения
попадают следующим input относительно подтверждённой базы. Локальный cached
native-результат не создаёт нового visit/input или якобы нового обращения модели.

Store проверяет неизменяемость замороженной доставки, монотонность acknowledgement
и принадлежность базы. Ответ старого владельца не может сохранить acknowledgement
или продвинуть cursor после takeover. Новых сетевых ожиданий и write-транзакций
для доставки нет: сборка синхронна, acknowledgement добавлен в прежние fenced writes.

`stop` не подтверждает неподтверждённые inputs и сохраняет аудит принятых решений.
`steer` до admission меняет/заменяет draft, после admission создаёт последующее
посещение. Групповой barrier не заменяет отдельный acknowledgement каждого child.
Scientist correction остаётся отдельным saved input в прежней сессии; старый
input не размораживается и не получает повторную доставку контекста.

## Implement и UI

Все implement-роли используют тот же механизм. `alpha/worker`, `alpha/reviewer`,
`beta/worker` имеют независимые базы даже при общих node-шаблонах. Возврат findings,
scoped-steer, dependency refresh и конфликтные материалы входят в актуальный
снимок/дельту. Event cursor scheduler по-прежнему отвечает только за пробуждение
manager, не за доставку модели; чужие interleaved события не меняют frozen input.

`taskContext`/UI `taskData` — полный логический снимок этого посещения, чтобы UI
не восстанавливал требования из цепочки patch. `prompt`/`promptRaw` — точные
отправленные байты, которые могут содержать дельту. UI call также отдаёт
`contextDelivery` с базой, видом и фактом acknowledgement. Старые raw-only записи
остаются raw-only. Наличие сохранённого снимка само по себе не доказывает отправку.

## Проверки и измерение

```sh
node --test context-delivery.test.mjs
npm run test:product
node --test --test-name-pattern='public CLI delta delivery' acceptance/runtime.test.mjs
node --test --test-name-pattern='implement participants read pinned' acceptance/implements.test.mjs
npm run test:runtime
```

Unit-проверка независимо применяет wire patch и сопоставляет результат с полным
актуальным снимком: точные решения/CRLF, удаления, JSON Pointer escaping, смена
порядка результатов, новые/старые сессии, memory:false, неподтверждённые drafts,
группы и scoped implement, SQLite takeover и запрет позднего acknowledgement.

Воспроизводимый корпус — восемь пакетов `acceptance/context-fixture.mjs`, четыре
возврата manager, в каждом новый отчёт (400 повторений `evidence `) и новое
решение с источником. Сумма JSON `.length` (UTF-16 code units, **не токены**):
**29 392** в четырёх дельтах против **68 446** в четырёх полных снимках, **−57,1%**.
Старые маркеры результатов и решений отсутствуют в последующих новых inputs;
каждая дельта восстанавливает полный снимок без потери данных. Длина временного
пути может немного менять абсолютные числа.

Native CLI-пробы используют отдельные Git/state/OpenCode-каталоги и управляемый
локальный HTTP provider, не ведущий сервис. Новые сценарии проверяют сбой после сохранения prepared/send-intent
до отправки, а также теряют acknowledgement второго, уже delta-input (crash и потерянный ответ), принимают позднее решение,
проверяют неизменные повторы, четыре разных inputs вместо скрытых retry-visits
и native read актуального fallback при намеренно отброшенной модельной памяти.
Это проверки доставки, не качества самостоятельного решения живой моделью.
Сохранность ссылок ограничена сохранностью локального runtime-каталога, как в xit.2.
