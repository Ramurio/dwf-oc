# Исследование через research-mid

Пресет запускается из каталога с материалами исследования. Каталог может
содержать первичные тексты или быть пустым для поиска по открытым источникам.

```sh
dwf preset save research-mid --file /path/to/dwf-oc/workflows/research-mid.json
dwf start --preset research-mid --task-file /path/to/research-question.txt
dwf inspect <runId> --watch
```

В OpenCode со скиллом `dwf-oc` можно сказать «Запусти DWF research-mid для
исследования ...». Для самостоятельной сборки скилл описывает связи ролей
и команды CLI.

Учёный получает результаты двух скаутов и каждой четвёрки исследователей
одним сообщением в своей сессии. Комитет начинает каждую проверку в отдельной
сессии и получает исходное поручение и отчёт. Он может открыть источники
для проверки. DWF ограничивает общий цикл тремя исследовательскими раундами.
Для смены исходного поручения останови запуск и запусти пресет с новым текстом.

В `result.summary` находится итоговый отчёт. `result.outcome` равен
`approve` для одобренного отчёта. При `changes` отчёт содержит замечания,
оставшиеся после третьего раунда. `status: "succeeded"` означает, что
DWF завершил процесс и сохранил результат.

## Поиск и чтение

Роли с доступом к источникам используют `read`, `glob`, `grep` и `webfetch`.
Учёный синтезирует результаты и может загрузить скилл синтеза. У него нет
инструментов чтения файлов и конфигурации комитета.

В OpenCode 2.2.5 штатный `webfetch` вернул страницы arXiv, поиск arXiv,
HTML QServe и ответы Crossref и GitHub API. Ответ Crossref на пробный запрос
содержал нерелевантные результаты. Ссылки из каталога требуют проверки
по тексту статьи или исходникам. Штатный `websearch` в двух вызовах
вернул ошибку, поэтому поиск по каталогам выполняется через `webfetch`.

Загрузка PDF через `webfetch` вернула ошибку формата. Для сравнительных проб
PDF переводятся в текст через PDFKit до запуска DWF. Сверка сложных таблиц
и рисунков может потребовать оригинал. Для расчётов в сравнении используются
условия из источников и внешняя арифметическая сверка. Исследовательские
роли имеют доступ к чтению и поиску.

## Как устроено сравнение

- По ReportBench взяли идею проверки утверждения по тому первоисточнику,
  на который оно ссылается. Код опубликован под Apache 2.0. Совпадение
  списка литературы покрывает только один аспект качества.
  [ReportBench](https://github.com/ByteDance-BandAI/ReportBench)
- DeepResearch Bench II разделяет экспертные требования на наблюдаемые
  пункты. Используем собственные пункты по задачам и отдельно оцениваем
  анализ. Код исходного проекта под Apache 2.0, у данных лицензии отдельных
  заданий. [DeepResearch Bench II](https://github.com/imlrz/DeepResearch-Bench-II)
- В ALCE полнота ссылок и поддержка утверждения ссылкой оцениваются
  отдельно. Здесь независимый оценщик проверяет отрывки и отдельно
  учитывает пробелы в ответе. [ALCE](https://arxiv.org/abs/2305.14627)
- BrowseComp проверяет поиск труднодоступного факта. Это ориентир для
  испытания поиска скаутов. В нашем пилоте основной объект оценки —
  длинный отчёт по зафиксированному корпусу.
  [BrowseComp и данные](https://openai.com/index/browsecomp/)
- Параллельное делегирование разных вопросов и различимые назначения
  инструментов опираются на опыт авторов многоагентной исследовательской
  системы. Для проверки выбора поиска полезен подход AstaBench с ограничением
  материалов по дате. Asta предлагает отдельный инструмент научного поиска.
  Наш пилот проверяет штатные инструменты OpenCode.
  [Многоагентная система Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system),
  [Asta Resources](https://allenai.org/asta/resources)
- Рассмотрены `literature-review` и `citation-management` K-Dense под MIT,
  а также скиллы Asta под Apache 2.0. Первые рассчитаны на отдельные
  скрипты поиска и библиографии, второй набор на интеграцию с Asta.
  DWF использует короткие ролевые скиллы на штатных инструментах. Из этих
  подходов взяты разделение поиска и оценки полного текста, фиксирование
  границы поиска и проверка метаданных у первоисточника.
  [Literature Review](https://github.com/K-Dense-AI/scientific-agent-skills/blob/main/skills/literature-review/SKILL.md),
  [Citation Management](https://github.com/K-Dense-AI/scientific-agent-skills/blob/main/skills/citation-management/SKILL.md),
  [Asta Plugins](https://github.com/allenai/asta-plugins)
- Из GEPA взяли рефлексию над журналом и конкретную гипотезу изменения.
  Код GEPA под MIT. Наш запускатель передаёт обратную связь отдельному агенту
  и сравнивает фиксированные ревизии. Темы для финала отделены от рабочих.
  [GEPA](https://github.com/gepa-ai/gepa),
  [Препринт о проверке на новых темах](https://arxiv.org/abs/2610.12601)
- Один модельный оценщик может предпочитать объём, стиль или ответы своей
  модели. Оценщик здесь получает один отчёт без статуса комитета и названия
  версии, проверяет утверждения по корпусу и выдаёт отдельные оценки.
  Тест комитета использует известные правильные и повреждённые отчёты.
  [Исследование смещений модельного оценивания](https://arxiv.org/abs/2306.05685)

Манифест `acceptance/research/cases.json` задаёт вопросы, границы по датам,
версии источников и их лицензии. Публичные оригиналы загружаются в локальный
каталог для испытаний. Тексты источников, закрытые критерии и журналы
остаются в локальном контуре. В нём сохраняются контрольные суммы загрузок
и снимков, версии DWF и скилла, запросы модели и затраты.

## Повторение испытаний

Нужны macOS с PDFKit и `sandbox-exec`, Node.js по требованиям проекта,
установленные зависимости и штатный вход OpenCode в профиль DWF. Каталог
проб должен находиться вне рабочего проекта.

```sh
python3 acceptance/research/prepare-corpus.py /path/to/research-evaluation quantization git-history
node acceptance/research/trial.mjs /path/to/trial-settings.json
node acceptance/research/assess.mjs /path/to/assessment-settings.json
node acceptance/research/compare.mjs /path/to/comparison-settings.json
```

Настройки прогона включают `root` с подготовленным корпусом, `caseId`,
`runtimeRevision` для архива кода и `skillDirectory` с версией скилла
`dwf-oc`. В `hidden` передаются пути к закрытым файлам. Проверка
границы проверяет отказ в чтении каждого пути и отсутствие доступа
к постороннему локальному сервису. Для проверки повторного запуска можно
указать `presetFile` с ранее выбранной схемой.

Для `assess.mjs` режим `score` получает каталог попытки в `trial`
и закрытый JSON в `rubric` с полями `questionId` и `criteria`.
`criteria` сопоставляет идентификаторы проверяемых утверждений с вопросами
и ориентирами в первоисточниках. `run-score` запускает тестера и оценщика
последовательно. `committee` принимает `fixtures` с контрольными отчётами,
а `propose` принимает `trials` с уже оценёнными рабочими попытками.
Предложение агента применяется отдельным изменением в рабочей ветке.

В сравнении передай `pairs` с каталогами `baseline` и `candidate`,
`hypothesis`, `change` и `output`. Сравнение проверяет совпадение корпуса,
поручения, критериев и протокола оценщика. Кандидат должен пройти проверки
точности и ссылок и повторить выигрыш по качеству или уменьшение расхода
токенов участников хотя бы на 15%.
Зафиксируй выбор до прогона отложенной темы. Для такой темы
`selection: false` сохраняет сравнение без повторного выбора версии.
