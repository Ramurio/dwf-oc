# Параллельные implement в одном workflow

[Workflow/CLI](workflow.md) · [Пакеты задач](task-packages.md) ·
[Полный пример](../workflows/parallel-implement.json)

Контракт xit.4. Это экземпляры задач внутри **одного** runId, не вложенные
CLI-запуски. Старые плоские графы и одношаговые `groups` сохраняют свою семантику.

## Схема и поручения

```json
"implements": {
  "concurrency": 2,
  "instances": {
    "alpha": {"taskId":"alpha", "worker":"work", "reviewer":"review", "verifier":"verify"},
    "beta":  {"taskId":"beta",  "worker":"work", "reviewer":"review", "verifier":"verify"},
    "gamma": {"taskId":"gamma", "worker":"work", "reviewer":"review", "verifier":"verify"}
  }
}
```

- `concurrency` — обязательное положительное целое, **default отсутствует**.
  В примере `2` выбрано явно для двух независимых задач. Слот занят всем активным
  циклом, включая reviewer/verifier, а не только работой worker. Готовый результат
  или ожидание решения освобождает слот. Объединения сериализованы.
- ID экземпляра — идентификатор графа (`[a-zA-Z][a-zA-Z0-9_-]*`, кроме
  `__proto__`, `constructor`, `prototype`), не имя узла/группы. `taskId` — явная уникальная
  ссылка на пакет того же workflow. У каждой зависимости тоже должен быть экземпляр.
- Узлы ролей — шаблоны настроек, могут обслуживать несколько экземпляров.
  Участники и сессии **разные**: `alpha/worker`, `beta/worker`, и т.д.
  Обычный цикл шаблонов задаётся переходами worker.done → reviewer,
  reviewer.approve → verifier, reviewer.changes/verifier.changes → worker.
  Внутри implement `verifier.approve` означает готовность результата, не завершение
  общего workflow. Шаблоны не используются как отдельные этапы или члены `groups`.
  Проверки обязательны; эффективное `memory:false` для этих ролей недопустимо.
- Нужны отдельные обязательные reviewer **и** verifier общего результата,
  даже при `merge:false`. В примере это `integrationReview`, `integrationVerify`.
- Поддерживается Git/worktree, не `workspace:"directory"`.

В граф добавляется адресат `implements` и переход:

```json
"manage": {"dispatch":"implements", "finish":"integrationReview", "done":null},
"implements": {"done":"manage"}
```

Только orchestrator допускает `implements`. Его результат, например:

```json
{
  "outcome":"dispatch",
  "summary":"Допустить независимые задачи; gamma дождётся их результатов",
  "implements":[
    {"action":"admit", "id":"alpha", "assignment":"Создать alpha.txt с содержимым alpha"},
    {"action":"admit", "id":"beta", "assignment":"Создать beta.txt с содержимым beta"},
    {"action":"admit", "id":"gamma", "assignment":"Проверить результаты alpha/beta и создать gamma.txt"}
  ]
}
```

Действия:

- `admit` — первоначальное конкретное поручение;
- `revise` — конкретное исправление готового, заблокированного, отрицательно
  проверенного или уже объединённого результата, в **его** worker-сессии;
- `integrate` — объединить готовый проверенный кандидат; поле `assignment` не нужно.

Массив проверяется целиком; повторные действия на один ID в одном решении
отвергаются. Сохранённое решение применяется один раз. Пустой массив ждёт.
Внутри цикла worker.done запускает reviewer, reviewer.approve — verifier.
`reviewer.changes` и `verifier.changes` автоматически возвращают замечания
ответственному worker в его прежней сессии, сохраняя исходное поручение и слот
цикла. Новое решение `revise` от orchestrator для такого возврата не требуется.
Управляющий процесс всё равно получает адресное событие `changes`; `blocked` и
ошибки требуют его решения. Принятый scoped-steer и устаревшие зависимости имеют
приоритет перед автоматическим продолжением. Другие экземпляры продолжают работу.
Замечания и поручения на исправление не превращаются автоматически в новые
требования пакета; уточнение требований пользователя сохраняется через `steer`.

## Очередь, события и контекст

Зависимости из пакета реально управляют **implement**, но по-прежнему не меняют
маршруты старых плоских узлов. Зависимый экземпляр начинает работу только после
объединения всех зависимостей в общий кандидат. Его исходный worktree уже содержит
эти файлы. Допущенная задача без слота ждёт `concurrency`.

Контроллер наблюдает фактические native-результаты и команды. Пока нет новых
результатов/вопросов/событий или управляющего действия, **нового вызова модели
orchestrator нет**. Переход к `implements` — ожидание, не модельный busy loop.
События `ready`, `changes`, `blocked`, `invalidated`, `conflict`, `integrated`, `decision_rejected`
имеют локальный монотонный `sequence`, implementId, taskId и фактические данные.
События, пришедшие во время решения orchestrator, не теряются при следующем ожидании.
Если scoped-steer сделал сохранённое решение устаревшим, весь набор действий
отклоняется событием `decision_rejected`; управляющий процесс получает новые факты,
а независимые циклы не останавливаются. Заведомо неверное решение на неизменном
контексте не вызывает бесконечный модельный цикл исправлений.

Единая сборка всех обычных и implement-inputs — `prepareRoleInput` из
`role-context.mjs` ([контракт xit.2](role-context.md)). Привязка остаётся общей:
`taskBinding(state,node,item)` с явным `item.taskId`. Каждый фактический visit
фиксирует `taskId/taskVersion`, `taskContext`, `contextDirectory` и точный `prompt`.
`rolePrompt` принимает готовый `context` последним аргументом; отдельного
implement-prompt или второго конструктора требований нет.

Общая структура `Task/context data` дополнена:

- `implement`: ID экземпляра, taskId, цикл, снимок и материалы конфликта;
- `assignment.implement`: точное адресное поручение, controllerInputId и ссылка
  на исходный отчёт manager, если он есть; `assignment.steering` сохраняет
  реальный источник пользовательского steer, не приписывая его старому manager;
- `otherReports.handoff/handoffSource`: findings и источник с inputId,
  scoped participant и implementId. Источник выбирается по сохранённому inputId,
  а не последнему соседнему visit или идентичности JS-объектов после restart;
- `dependencies`: прежний ID пакета и ссылка на него плюс отдельный implementId,
  фактический интегрированный снимок, resultVersion и чужой отчёт;
- для manager — `implements` с реальными экземплярами/событиями, фактические
  status/waitingReason в `catalog` и state-aware `control.approvalProblems`.

Контекст — отдельный JSON-снимок, без живых ссылок на события и операции scheduler.
После admission он не меняется; restart использует сохранённые данные, prompt,
sessionId и inputId. Если steer меняет ещё не допущенный group-child, новая
подготовленная версия получает отдельный inputId/каталог материалов; прежний draft
не переписывает immutable history после поступления соседних результатов.
UI получает тот же `taskContext` как `taskData`, отдельно от `promptRaw`.

Общий механизм разрешений xit.2 добавляет недостающий доступ к сохранённым contexts,
diff и доверенным копиям конфликта, сохраняя остальные правила прежней сессии.
Произвольные URI пакетов по-прежнему не расширяют права. Native-тесты проверяют
чтение закреплённых требований всеми тремя implement-ролями, повторный вход в ту же
worker-сессию, prepared restart и lost acknowledgement без пересборки контекста.
Курсор доставки и acknowledgement реализованы в [xit.3](context-delivery.md):
база отдельна для каждой scoped роли и её сессии, новые inputs могут быть дельтами.
Ограничения размера/clipping нет. Событийный sequence здесь не является delivery
cursor и не доказывает доставку модели.

## Кандидаты, исправления и одобрения

У экземпляра свой постоянный worktree. Reviewer читает полный diff относительно
базы его текущей работы; verifier получает отдельный снимок переносимых файлов,
как в прежнем runtime. Все три роли имеют отдельные сохраняемые сессии. Возврат
worker не создаёт новую сессию. Для reviewer/verifier сессия перемещается в актуальный
каталог, когда это требуется native API.

Готовность требует worker.done и reviewer/verifier.approve **одного текущего
снимка и версии пакета**, а также актуальных результатов зависимостей. Изменение
файлов соседнего изолированного кандидата не отменяет это одобрение. Изменение
собственного проверяемого дерева отменяет его; интеграция такого результата
возвращает `invalidated`, не переносит непроверенные файлы в общий кандидат.

Проверки экземпляра никогда не заменяют проверки общего дерева. Завершение требует:

1. Все объявленные экземпляры проверены и объединены.
2. Их кандидаты и зависимости всё ещё соответствуют одобренным результатам.
3. Отдельные обязательные проверки одобряют текущий общий снимок.
4. Для внешнего merge также выполняются прежние проверки исходной ветки,
   чистоты и соответствия коммита одобренному дереву.

Если проверка интеграции требует исправления, orchestrator возвращает `revise`
соответствующему implement. Его worker сохраняет сессию; новый кандидат начинается
от актуального общего снимка с сохранением ещё не объединённых локальных изменений.
Повторное открытие объединённого результата аннулирует зависимые результаты,
**не** независимые approvals. Активный зависимый input сначала фактически заканчивается,
затем получает `invalidated`; принудительно конкурирующий ввод в ту же сессию не
отправляется. Зависимые исправления ждут новой интеграции, получают обновлённые файлы
зависимостей и проходят свой цикл. `resultVersion` считает интегрированные результаты,
а не версии требований. Общие проверки выполняются повторно для изменённого дерева.

## Объединение и конфликты

DWF выполняет `integrate`, не модель. До Git-изменений сохраняются ID операции,
ожидаемый общий снимок и исходный кандидат. Patch накладывается в отдельном scratch
worktree. Только успешное объединение переносится в общее дерево; исходный проект
при этом ещё не меняется. Replay восстанавливает scratch из сохранённой базы и
различает состояние до/после переноса. Чужие непредусмотренные изменения общего
дерева не перезаписываются. После завершения всех проверок прежний `mergeWorkspace`
может сделать внешний локальный fast-forward, если задано `merge:true`.

При конфликте остаются:

- исходный результат каждого implement и исходное общее дерево;
- отдельный scratch с конфликтами;
- binary/full-index patch, список конфликтующих путей, базы и снимки операции;
- отдельный снимок исходного кандидата verifier, история операций и результатов.

Событие адресовано ответственному implement. По `revise` DWF переносит конфликтный
кандидат в его прежний рабочий каталог и отправляет исправление в **ту же** сессию
worker. Замена выполняется двумя сохранёнными фазами: сначала `integration.resolution`
фиксирует ожидаемые снимки рабочего, общего и конфликтного деревьев и отдельные
закреплённые копии рабочего кандидата (включая поздние правки и новые файлы) и
конфликтного дерева. Эта подготовка сохраняется до любого разрушительного reset.
Следующая фаза проверяет ожидаемые деревья; replay после аварии принимает только
исходный снимок или уже установленный конфликтный снимок. Неожиданные поздние
изменения останавливают замену без перезаписи файлов. Сохранённые оригиналы, в том
числе `resolution.candidateWorkspace` с поздними правками, доступны по путям из
контекста с ограниченным разрешением чтения. После исправления обязательны новое
ревью/верификация и новое решение об интеграции. Конфликт при обновлении зависимостей также сохраняет обе версии и
передаётся исправляющему worker. Обновление кандидата также проверяет ожидаемое
общее дерево и состояние рабочего каталога до/после замены; поздние правки после
подготовки не перезаписываются. Scratch/снимки остаются для аудита; автоматический GC
этих артефактов в xit.4 не добавлен.

Подготовленные замены `refresh`/`resolution` завершаются отдельным tick **без**
изменения общего дерева. Только после сохранения их результата scheduler продолжает
независимые интеграции. Поэтому одно решение `integrate alpha` + `revise beta`
допустимо и не нарушает собственные проверки ожидаемых снимков; replay после
аварии также не видит общего дерева, изменённого в том же незаписанном tick.
Эта фаза не допускает новые native inputs сверх `concurrency`: замену можно
завершить при занятых слотах, а worker продолжит ждать слот. Если зависимость
подготовленного refresh вновь открыта, старое намерение становится `superseded`;
новое готовится после её интеграции. Проверки неожиданных поздних правок остаются.

Успешная установка refresh (включая новый конфликт на актуальной базе) делает
прежний `integration.status: conflict` неактивным: он получает `superseded` и
`supersededBy: <refresh ID>` и сохраняется в `conflictHistory` со всеми scratch,
исходными копиями и patch. Старое конфликтное дерево больше не устанавливается
поверх обновлённого кандидата. Worker продолжает на файлах актуальных зависимостей;
если refresh сам конфликтует, его материалы и есть текущий `implement.conflict`.
Отметка superseded и новые версии зависимостей сохраняются вместе с результатом
замены; replay после аварии повторяет refresh, а не возвращает прежние файлы.

## CLI, inspect, UI и восстановление

```sh
node ./dwf.mjs schema
node ./dwf.mjs start --file /absolute/path/parallel-implement.json
node ./dwf.mjs inspect <runId>
node ./dwf.mjs inspect <runId> --watch
node ./dwf.mjs steer <runId> alpha --message-file correction.txt
node ./dwf.mjs steer <runId> alpha/reviewer --message-file review-note.txt
node ./dwf.mjs stop <runId>
```

`steer alpha` адресует worker; `alpha/worker|reviewer|verifier` — конкретную роль.
Неоднозначный общий шаблон `work` не является адресатом. Ввод доставляется после
завершения текущего native-input экземпляра; несколько уточнений не схлопываются
в последнее. При приёме сохраняется прежний аудит `taskRevisions` с источником
`steer:<UUID>`. Принятый/подготовленный ввод не равен подтверждённому inbox admission:
точный [контракт доставки xit.3](context-delivery.md) различает эти границы.

Публичный `inspect.implements`:

- `concurrency`, массив `instances` с ID/taskId, status, phase, cycle, worktree,
  candidateRevision, resultVersion, результатами и реальными scoped-участниками;
- `current` экземпляра: фактические inputId/sessionId и admission status/progress;
- `dependencies`, `waitingFor`, `waitingReason`: `assignment`, `dependencies`,
  `concurrency` или `controller`;
- операции интеграции/обновления кандидата, сохранённые конфликты и `events`.

Статусы кандидата: `pending`, `queued`, `running`, `changes_requested`, `blocked`,
`ready`, `integrating`, `conflict`, `integrated`. Общий `current` остаётся управляющим
этапом; при ожидании имеет role `implements` и waitingReason `implement_events`.
`history` содержит настоящие inputs с `implementId`, participant, taskId/taskVersion.
Маркер ожидания **не** native-участник и не сессия. UI/store читают эти поля, не
угадывают задачу по имени узла. UI adapter возвращает один workflow и платформу
`implements` с реальными участниками, состояниями и историей вызовов. Это контракт
данных для xit.5, не заявление о завершении её отдельного UI-дизайна.

Состояние, история inputs и операций остаются в прежнем `workflows.state` SQLite,
без дополнительного сервиса/таблиц. Перезапуск сохраняет активные, ожидающие и готовые
экземпляры. Сохранённые native sessionId/inputId и неизменный текст повторяются при
потере acknowledgement; inbox OpenCode дедуплицирует их. Внешние отправки и Git-действия
выполняются под прежним fencing владельца/транзакцией; stale owner не отправляет ввод.
Native metadata также фиксирует implementId, taskId и scoped participant; чужая
сессия того же runId не принимается за сессию другого implement.

`stop` охватывает все сессии/каталоги экземпляров, отменяет inbox, прерывает сессии
и подтверждает фактическую остановку shell-процессов/детей до `cancelled`.
Сохранённые статусы кандидатов не стираются; `executionStatus:cancelled` показывает,
что они уже не исполняются. При терминальной ошибке управляющего процесса runtime
сначала сохраняет `pendingFailure`, прекращает новые допуски и подтверждает остановку
всех сессий/команд; только затем выдаёт `failed` с `executionStatus:stopped` у экземпляров.
Потеря сервиса в этой фазе остаётся resumable, а не ложным подтверждением остановки.
Исходный проект не получает непроверенный результат.

## Проверки и границы

`workflow-implements.test.mjs` проверяет schema, изоляцию approvals, зависимости,
возвраты, конфликты, gates и UI-проекцию. `acceptance/implements.test.mjs` использует
кандидатный CLI, настоящий OpenCode/инструменты/Git, управляемый HTTP-провайдер
**только модели**, отдельные каталоги/профиль и очистку процессов. Он удерживает
одновременно worker, reviewer и verifier двух циклов, проверяет очередь третьего,
автоматический возврат замечаний при удерживаемом manager, адресные вопросы,
конфликт с сохранением поздних текстовых/binary-файлов, повторную интеграцию,
live takeover и crash admission. Отдельные Git fault-injection пробы покрывают
аварии после scratch apply, между двумя parent read-tree, после изменения общего
дерева и после каждого reset при установке конфликта в worker-каталог. Stop
проверяется на реальных устойчивых shell-процессах.

Это не реализация отдельных несделанных требований dwf-oc-vku/co1/hni или
xit.5. Доставка xit.3 описана [отдельно](context-delivery.md). Никаких заявлений о глобальном планировщике, динамическом добавлении новых
пакетов после старта, глобальном трекере задач или полной политике доставки контекста.
