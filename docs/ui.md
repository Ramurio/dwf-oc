# Общий локальный UI

```sh
dwf ui --start       # один фоновый сервер; JSON с localhost URL
dwf ui --status      # адрес уже работающего сервера (также dwf ui)
dwf ui --stop        # останавливает только UI; повторять безопасно
```

`dwf ui start|status|stop` — алиасы. Из исходников: `node /path/to/dwf/dwf.mjs ui --start`.
Открыть `url` из ответа в браузере. Команда завершается, сервер переживает закрытие
терминала, но не перезагрузку компьютера. Повторные и конкурентные start из разных
проектов переиспользуют сервер и URL. После stop/reboot/crash новый start может дать
другой порт. UI не нужен для исполнения workflow и не управляет им.

## Охват и хранение

Обычный общий каталог — `~/.dwf`: UI читает все проекты из его `dwf.sqlite`, включая
сохранённые запуски. Новый запуск из любого проекта поступает в открытый UI при
следующем опросе (обычно 1,2 секунды). Новейший запуск выбран при первом открытии;
обновления не переключают осознанный выбор или выбранный исторический вызов.

`DWF_STATE_DIR=/absolute/path` сохраняет существующую изоляцию: отдельная база,
отдельный UI, start/status/stop относятся **только к этому каталогу**. UI не сканирует
диск и не объединяет разные state roots или профили других пользователей. При
обычном использовании без override все проекты уже используют одну базу.

Миграции схемы и нового реестра проектов нет. Новые запуски сохраняют `createdAt`
в существующем JSON состояния/запроса; старые записи не переписываются. Старые
workflow используют первое сохранённое время посещения. Если времени нет вовсе,
показывается `Time not saved`; такие записи следуют за датированными, с устойчивым
порядком вставки внутри таблицы. Точный взаимный возраст старых planner/workflow
без timestamps восстановить нельзя.

`ui.json` — заменяемая приватная runtime-регистрация (URL, instance, PID с
идентичностью процесса и случайный control token). Не переносить её между машинами
и не публиковать. Start проверяет регистрацию и безопасно заменяет устаревшую;
PID не используется для остановки чужих процессов. Общий короткий SQLite lock
сериализует конкурентные start/stop. Зависший, но идентифицированный UI не порождает
дубликат. Если stop не может получить подтверждение, команда завершается ошибкой,
а не заявляет об успешной остановке.

Сервер слушает только `127.0.0.1` на автоматически выбранном порту. Проверяются Host
и Origin; управление остановкой требует token. Нет CORS, удалённых assets, workflow
controls и произвольной выдачи файлов. Это локальный просмотр приватных заданий,
не механизм защиты от других процессов того же пользователя.

## Наблюдения, карта и сессии

- Карта строится из определения и посещений: переходы с одинаковыми концами
  объединяют подписи исходов, а не теряют их. DFS автоматически выделяет обратные
  дуги произвольных циклов; встречная линия существует только при настоящем
  встречном переходе. Координат под имена запусков нет.
- Шаблон участника, исполняемый только внутри группы, находится внутри группы, а
  не дублируется как отдельный исполняемый этап. Его собственные переходы не
  исполняются при завершении дочернего вызова. Самостоятельно адресуемые или
  наблюдавшиеся вне группы участники получают отдельные платформы.
- Группы показывают реальные роли каждого участника; сохраняются старые items и
  посещения, включая последующие самостоятельные обращения к участнику. Размер
  data-driven группы меняется по наблюдаемому составу, не по выдуманному списку.
- Если один участник вызывается самостоятельно и внутри групп, история остаётся
  общей, но подсветка относится только к фактической платформе текущего вызова.
  Сводка не дублирует участника, а кнопка перехода к текущему открывает именно
  работающую платформу. При самостоятельном уточнении mapped-участника сохраняется
  его настоящий participant ID и показывается фактический узел-шаблон исполнения.
  В историческом вызове указано другое место исполнения. Если у самостоятельного
  узла несколько participant ID, в деталях доступен их переключатель: прежняя
  самостоятельная identity не теряется после mapped-steering. Переключатель есть
  и при отсутствии наблюдавшихся вызовов у выбранной identity. Подготовленный,
  но ещё не подтверждённый input не считается вызовом и не вытесняет наблюдавшуюся
  историю из начального просмотра блока.
- Геометрия зависит от структуры и подписей, не от статуса или выбранной истории.
  Сохранены Lines, парный зазор 6px, forward 2.3px, return 1.25px, наконечники поверх
  масок, Fit, zoom и pan. Изменение самого состава группы может изменить её размер.
- Счётчик содержит подтверждённые/наблюдавшиеся вызовы (`admitted`, результат или
  progress), не просто выделенные session IDs или подготовленные send intents.
  Сохранённая коррекция ответа — отдельный вызов. При потере acknowledgement до
  наблюдения вызов может временно не учитываться: это не выдуманное выполнение.
- След контекста сравнивает настоящие session IDs. При отсутствии ID продолжение
  не утверждается. Task использует сохранённые структурированные данные, если они
  есть; Technical prompt раскрывается отдельно. Записи без таких данных честно
  обозначены Task (raw prompt only), без реконструкции критериев из текста.
  [Контракт адресных данных](role-context.md). Видны результат, история, сохранённая модель
  и reasoning. Основной Result для DWF-envelope — настоящий `summary`, без
  служебного `outcome` и JSON-скобок. Замечания, артефакты, commit и прочие сохранённые
  поля раскрываются отдельными читаемыми частями; точный исходник доступен через
  закрытый по умолчанию `Original saved result`. Это работает и для итога всего
  workflow; произвольные старые объекты/массивы и обычный текст не теряются.
  Скорость сейчас не сохраняется runtime и помечена `Not recorded`.
  Раскрываемые skills — сохранённые разрешённые навыки с доступным точным содержимым
  версии; это **не свидетельство их фактического использования**. Отсутствующие
  настройки старых записей явно неизвестны.
- Running без действующей аренды контроллера помечен как неподтверждённый,
  а не как работающая модель или завершённая ошибка. Возобновление — явный
  `dwf inspect <id>`, не побочный эффект открытия UI. Terminal включает succeeded,
  failed и cancelled. Потеря соединения оставляет последний просмотр и историю.
- Старый planner-формат также поддерживается. UI только наблюдает уже существующий
  сервис OpenCode, проверяет принадлежность сессии и сохраняет подтверждённый итог
  тем же способом, что inspect. Не создаёт сервис, сессию или повторный ввод.

Команда входа использует установленный в этом DWF **OpenCode 2.2.5**:
`opencode --session <sessionID>`, **без позиционного исторического каталога**.
Она включает абсолютный путь к закреплённому CLI и сохранённое окружение профиля;
аргументы экранированы для POSIX shell. Отсутствие старого saved profile означает
прежний изолированный профиль `DWF_STATE_DIR/opencode`, как и в runtime.

Согласованный контракт: открыть существующую сессию выбранного участника в её
**текущем нативном контексте**, а не переносить её в каталог старого вызова.
OpenCode 2.2.5 игнорирует позиционный каталог при открытии существующей сессии.
UI не вызывает `session.move`, fork, prompt или admission; скопированная команда
тоже не содержит этих действий. Возобновление работы — последующее решение
пользователя уже в OpenCode.

В деталях отдельно отображаются:
- **This call · saved directory** — сохранённый каталог выбранного вызова;
- **Current session directory · OpenCode observation** — `session.get().location`
  из уже работающего сервиса с проверкой принадлежности запуска. UI только
  обнаруживает сервис, не запускает его. Это наблюдение, каталог может измениться
  до исполнения скопированной команды;
- если сервис/сессия недоступны, текущий каталог явно **Unknown**, а **Last saved
  session directory · not a live observation** показывает последний наблюдавшийся
  в данных DWF каталог этой сессии. Он не выдаётся за её фактическую location.

При отличии исторического каталога от наблюдаемого текущего UI объясняет, что
OpenCode откроет текущий контекст, **не исторический worktree**. История раннего
вызова, его prompt/result и session ID остаются доступны. Команда открывает ту же
сессию независимо от выбранного вызова. Если native API подтвердил отсутствие
сохранённой сессии, команда не предлагается. Удалённые пользователем сессии и
рабочие деревья UI не восстанавливает; доступность может измениться после чтения.

## Общие assets и воспроизведение

`prototypes/dwf-ui/{app.mjs,layout.mjs,styles.css,index.html}` — единственные общие
Lines-assets. Сервер `ui-server.mjs` выдаёт их с live-маркером; `ui-data.mjs` адаптирует
данные, `ui-service.mjs` отвечает за жизненный цикл. Никакие fixtures не загружаются
live-сервером. Статическая выдача той же папки остаётся явно обозначенным
fictional demo для воспроизводимых визуальных проверок. `baseline.html` не менялся.

```sh
npm ci
npm test
npm run test:ui
node prototypes/dwf-ui/qa/browser-checks.mjs
node prototypes/dwf-ui/qa/review-regressions.mjs
```

`acceptance/ui-view-regressions.mjs` (в составе `test:ui`) дополнительно проверяет
на управляемых сохранённых записях `r → batch(r)`, общую историю без двойной
активности, узел `toString`, самостоятельный вызов mapped-участника, выбор всех
identity узла (включая ещё не admitted input) и читаемый
`{outcome, summary, findings, artifacts}`. Исходные значения, включая `false` и `0`,
сохранены; раскрытия и выбранный вызов переживают обновление. Это view-проверка,
не свидетельство исполнения подставленных сессий; настоящие сессии отдельно
проверяются в `acceptance/ui-browser.mjs`. Адаптерные тесты дополнительно покрывают
`hasOwnProperty`/`valueOf` и обратные дуги с такими именами.

Browser QA требует Chrome (`CHROME_BIN` для другого расположения), Python 3 для
отдельного PTY и macOS/Linux. Используются временный `DWF_STATE_DIR`, собственные
OpenCode/Chrome-профили, автоматические debug-порты и локальный управляемый
HTTP-провайдер модели; пользовательские сервисы не останавливаются. Сырые журналы,
скриншоты и отчёты в `.evidence/` / `acceptance-results/` исключены из Git.

Проверено в macOS, Node 26.8.1, OpenCode 2.2.5, Chrome: конкурентный singleton,
проверка реального loopback-сокета, зависший UI без дубликата, stop/restart и crash
со stale registration; два настоящих CLI-проекта и новое поступление в браузер;
running → terminal; сохранение выбора, истории и геометрии; потеря/возврат связи;
смешанные fixed и повторные data-driven группы; старый planner; копирование с
чтением clipboard и открытие **сгенерированной команды** в PTY с проверкой названия
выбранной настоящей сессии. Также проверены геометрические инварианты для
сгенерированных валидных определений с циклами из 3–9 участников, несколькими
возвратами, self-loops и длинными именами, плюс существующая Lines QA.

Платные внешние модели в UI QA не вызывались. Перезагрузка ОС и закрытие настоящего
терминального приложения не автоматизировались: отделение проверено выходом
родительского CLI и сохранением работающего HTTP-сервера. Другие браузеры и очень
большие базы пока не benchmark-ились; текущий адаптер выдаёт полный снимок базы,
без скрытого лимита запусков. Git-интеграцией, ревью и публикацией этого изменения
управляет внешний DWF workflow; эти проверки сами по себе не означают merge/push.
