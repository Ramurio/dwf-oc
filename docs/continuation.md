# Продолжение существующего запуска

```sh
node ./dwf.mjs continue <runId>
node ./dwf.mjs inspect <runId>
node ./dwf.mjs inspect <runId> --watch
```

Исправьте причину ошибки (например, права провайдера после HTTP 403), затем
используйте **тот же runId**, не новый `start` и не правку SQLite. Команда
сохраняет worktree, определения и точные требования, решения, сессии, результаты
и историю. `running` с действующим владельцем и `succeeded` не запускают второго
исполнителя. После смерти контроллера его аренда действует до 30 секунд;
повторите `continue` после истечения аренды, если владелец ещё числится работающим.

## Проверяемая граница

- Подготовленный/неподтверждённый ввод повторяется с сохранёнными inputId,
  sessionId и байтами; native inbox дедуплицирует приём после потери ack.
- Работающий native input/его shell не заменяется новым поручением.
- Сохранённый или доступный native-результат сначала используется на прежнем
  этапе. Подтверждённая ошибка даёт отдельный input в прежней сессии и сообщение
  продолжения; старая ошибка не стирается. Успешные прежние этапы не повторяются.
- Для группы повторяется неуспешный участник, а не успешные соседи. Recheck
  смешанной группы сохраняет успешные writer inputs/results; уже интегрированные
  writer-патчи не применяются повторно. Решения неопределённых checking-операций
  привязываются к фактически отправляемым новым children и проверяются до send. Git-операции
  групп/implement сверяют сохранённые исходные и итоговые деревья. При потерянном
  подтверждении внешнего merge проверяется фактический HEAD/дерево исходной ветки;
  повторное объединение уже перенесённого результата не создаёт новый коммит.
- Незавершённый текущий этап сначала заканчивается: retry/подключение worker или
  активного native input не вытесняется историческим recheck.
- Изменённые файлы не получают старые approvals: проверяющие возвращаются на
  текущий снимок. Изменённый implement-кандидат требует свежего worker/checking
  цикла, зависимые результаты инвалидируются, независимые сохраняются.
- Потерянная native-сессия не выдаётся за восстановленную историю. После явного
  решения создаётся новая сессия с сохранённым контекстом/исходным вводом и
  предупреждением о недоступных native-сообщениях.

Проверка/продолжение fenced той же транзакцией SQLite, что takeover, stop,
steer и финализация. Неизменяемые inputs не размораживаются. Журналы
`failures` и `recoveryHistory` дополняются, а не очищаются.

## Явная остановка

`cancelled` не возобновляется обычным `continue`:

```sh
node ./dwf.mjs continue <runId> --resume-cancelled
```

Флаг означает явное намерение пользователя продолжить этот запуск. Исходный stop
остаётся в controls с `resumedBy`. Если остановка прервала произвольную команду,
одного флага недостаточно: требуется также решение её неопределённого результата.

## Неизвестный внешний результат

Если нельзя установить исход команды/утраченной сессии, команда сохраняет прогресс
и возвращает `recovery.status: blocked`, конкретные `problems` и готовую форму
`recovery.resolutionTemplate`. **Ничего неопределённого молча не повторяется.**
Скопируйте весь template в UTF-8 JSON-файл. Для каждой записи `decisions` задайте:

- `action: "confirm"`: пользователь проверил внешний результат; `evidence`
  описывает наблюдение. Это свидетельство пользователя, не успешный отчёт DWF
  и не замена reviewer/verifier. Продолжающий участник проверяет сохранённую работу.
- `action: "retry"`: пользователь явно разрешает повтор этой операции, понимая
  возможные дубли внешнего эффекта. `evidence` описывает разрешение/ограничения.
- `action: "abort"`: прекратить восстановление, сохранив прогресс и решение.

Не меняйте `runId`, `token`, `operationId`, `attemptId`, `revision`. Заполните
`evidence`; исходный template намеренно не является готовым разрешением.

```sh
node ./dwf.mjs continue <runId> --resolution-file decision.json
# Для cancelled нужны оба явных действия:
node ./dwf.mjs continue <runId> --resume-cancelled --resolution-file decision.json
```

Решение охватывает только перечисленные операции, попытки, фактические деревья,
состояние native inputs и принятые управляющие команды. Изменение этих данных
делает файл устаревшим: снова вызовите `continue` без файла и перепроверьте факты.
Произвольные результаты не синтезируются из `confirm`. Внешние ошибки окружения,
сессии, Git или повреждённого состояния требуют исправления, не обхода проверок.

## Наблюдение и совместимость

`inspect` показывает `current.inputId/admission`, исходные ошибки в history,
новые `recoveryOf/recoveredBy`, `failures`, `recovery` и `recoveryHistory` с планом
и решениями. UI показывает recovery в описании запуска и подробностях результата,
новые и старые вызовы — в истории участника. Заблокированное восстановление
не запускается автоматически наблюдателем. `stop` остаётся доступным для
приостановленного running-запуска.

Старые workflow без delivery/taskContext продолжаются с сохранёнными raw-inputs;
данные не «восстанавливаются» разбором prompt. Неудачный одношаговый planner
представляется в общем workflow runtime под тем же ID, сохраняя исходную запись
`runs` как `legacyPlanner` и исходный профиль/сессию. Успешные legacy-запуски
не преобразуются. Одноразовые ручные исторические восстановления не считаются
использованием этой команды и не удаляются из аудита.

Проверки и точные границы свидетельства: [матрица продолжения](continuation-verification.md).
