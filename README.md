# DWF — независимое исполнение workflow на OpenCode

Исходники проекта — [Ramurio/dwf-oc](https://github.com/Ramurio/dwf-oc).
Полный промпт автономного развития и испытаний находится в [docs/autonomous-goal.md](docs/autonomous-goal.md).

## Назначение и пользовательский путь

DWF позволяет внешнему агенту собирать кастомные workflow на лету и запускать
готовые пресеты. Базовый блок — участник с ролью. Минимальный набор ролей —
`worker`, `reviewer`, `verifier`, `orchestrator`. Связи определяют передачу работы,
проверку результата, возврат на доработку и условия завершения.

Пользователь описывает нужный результат в контексте своего проекта. Агент сам
определяет этот проект, выбирает пресет либо собирает workflow и запускает DWF.
Установка DWF, пути к его файлам и настройка модельного транспорта скрыты за
обычной командой `dwf` и скиллами. При нескольких подходящих проектах агент
уточняет выбор. Текущий каталог вызывающего CLI задаёт рабочий проект.

Агент составляет workflow по конкретной задаче пользователя. Состав участников,
их инструкции и переходы задаются в JSON. Повторный вход в узел сохраняет его
сессию и историю. Роль orchestrator можно использовать для итогового отчёта,
когда этого требует задача. Переходы и интеграцию выполняет DWF.

Пресет — workflow, сохранённый пользователем или агентом для повторного
использования. Встроенных пресетов нет. В пользовательской пробе агент сам
собирает процесс из worker, reviewer и verifier, включая возврат замечаний
прежнему worker и локальный merge после успешных проверок.

## Действующий прототип

CLI исполняет workflow из ролей, возвращает идентификатор и завершается.
Отдельный контроллер ведёт переходы, OpenCode исполняет роли, другой вызов CLI
получает сохранённое состояние и результаты. Каждый узел сохраняет собственную
сессию при возвратах. Используется OpenCode **2.2.5** и отдельная SQLite DWF. Зависимости
и авторизация Pi удалены из действующего продукта и тестов.

**Ранее проверенный срез одного планнера, 2026-11-07.** Прошли 19 самопроверок и 7 исполняемых сценариев
из 79 шагов, включая настоящую модель. Выполнен цикл рабочая версия → целевая
поломка жизни исполнителя → побайтовое восстановление → успешная приёмка.
Отдельно проверены холодный параллельный запуск, восстановление после аварии,
получение сохранённого в OpenCode ответа до первого успешного `inspect` и
штатные продолжения по длине. По просьбе пользователя реализацию и проверку
этой итерации выполнил один агент.
[Итоговый отчёт](acceptance-results/opencode/implementation-report.json).

Ролевой workflow проверен отдельно на копии Pocket Tasks. Настоящие worker,
reviewer, verifier и orchestrator завершили задачу, DWF выполнил локальный merge,
после которого прошли 11 тестов. Управляемые сценарии дополнительно проверяют
возвраты обоих проверяющих, прежние сессии и восстановление контроллера.
[Отчёт по workflow](acceptance-results/opencode/workflow-report.json).

Автономная серия расширила проверку индивидуальными профилями участников,
актуальностью обязательных одобрений, параллельными группами, steering,
остановкой и восстановлением после аварии. Полный `npm test` на `84a36dd`
прошёл 30 проверок контура, 62 проверки продукта, 12 Cucumber-сценариев
из 116 шагов и 21 native-проверку на OpenCode 2.2.5.

Независимые тестеры выполняют задачи p-limit, Click, Expr и more-itertools из чистых исходных
ревизий. Для каждого из четырёх проектов получены по две чистые принятые попытки
с внешней проверкой результата. Сводка сохраняет также
неуспешные попытки, точные версии runtime, хеши заданий и скиллов, затраты
и оговорки по регрессиям. Эталоны, скрытые проверки и сырые журналы хранятся
в отдельном проверяющем контуре. [Сводка испытаний](acceptance/benchmark-results.json).

В more-itertools обе принятые попытки исправляют удержание потреблённых элементов
в `ichunked`. Каждая прошла 13 независимых проверок и исходные тесты проекта.
Предыдущий случай добавления `ichunked` исключён из приёмки, поскольку его эталон
не прошёл дополнительную проверку памяти. Во второй принятой попытке reviewer
также потребовал поведение после ошибки, ошибочно приписанное исходной версии.
Этот дефект качества ревью учитывается отдельно в `dwf-oc-2dp.2`.

В контролируемом сравнении оба варианта системных промптов прошли по 16
случаев на восьми сценариях с двумя повторами. Действующие промпты сохранены.
[Корпус, методика и ограничения](docs/prompt-comparison.md).

Дополнительная серия проверяет утверждения reviewer о поведении исходной версии
и передачу непроверенных гипотез verifier. [Результаты и ограничения](docs/reviewer-baseline-comparison.md).

По решению пользователя текущая модель — **GPT-6.1 Sol**, reasoning **high**.
Используется штатная запись OpenCode `gpt-6.1-sol-ultrafast`, соответствующая
пункту «GPT-6.1 Sol Ultrafast» в меню. Она отправляет `gpt-6.1-sol` с
`service_tier: "ultrafast"`.
Передача параметра и доступность режима для аккаунта проверены. В опыте со
штатными записями без ручной настройки скорости одинаковый вывод из 2006 токенов
получен со скоростью 57,4 токена/с в Standard и 414,3 токена/с в Ultrafast,
ускорение 7,2 раза. Предыдущая серия из четырёх проб дала медианное ускорение
6,6 раза. Сырая метка `service_tier` в ответе ChatGPT/Codex осталась `default`;
она сохранена отдельно от выбранного режима и замера. Это проверка ускорения,
без доступа к внутренним данным планировщика и расчёта оплаты.
[Штатные записи](acceptance-results/opencode/ultrafast-native-model-probe.json),
[первая серия](acceptance-results/opencode/ultrafast-probe.json),
[каталог аккаунта](acceptance-results/opencode/ultrafast-catalog.json).
Будущие уровни reasoning будут выбраны по ролям.

## Скиллы участников

Worker получает один скилл `code-work` из `skills/worker/`. Он объединяет
проверку изменяемого поведения, диагностику сбоев и проектирование интерфейсов.
Исходник поддерживается в отдельном репозитории
[ramu-skills](https://github.com/Ramurio/ramu-skills/tree/main/skills/code-work).
DWF содержит его копию, поэтому запуск не зависит от расположения соседнего проекта.
После правки исходника обновляй `skills/worker/code-work/SKILL.md` той же версией.
OpenCode показывает краткое описание и загружает содержимое по вызову `skill`.
Reviewer получает наш `code-review` из `skills/reviewer/`, исходник которого также
поддерживается в `ramu-skills`. Копию обновляй из `skills/code-review/SKILL.md`
этого репозитория. Он сверяет изменения с поручением, проверяет корректность,
сохранность данных, ожидаемую нагрузку, качество тестов и обоснованность структуры.
Обязательные исправления должны иметь конкретное обоснование. Повторное ревью
проверяет устранение замечаний и регрессии от исправлений.

Verifier получает `code-verify` и выполняет независимые проверки поведения.
Orchestrator получает `workflow-summary` и составляет итог по истории этапов,
сопоставляя замечания, исправления, проверки и ревизии. Служебный planner старого
одноагентного сценария получает `task-planning` для составления текстового плана.
Его единственный инструмент — загрузка этого скилла. Эти три исходника также
поддерживаются в `ramu-skills`, копии находятся в `skills/<роль>/<имя>/SKILL.md`.

Каждое посещение reviewer получает путь и размер полного diff от исходной ревизии
workflow до проверяемого Git tree. Файл включает незакоммиченные изменения и
хранится отдельно от рабочего дерева. После доработки создаётся новый файл,
предыдущие материалы сохраняются. Большие diff читаются частями.

Адаптации используют требования и соглашения текущего проекта. Управление
переходами, сессиями и Git остаётся у DWF. Источники скиллов указаны в README
репозитория `ramu-skills`. Автор адаптаций — Ramurio.
Лицензия находится в `skills/LICENSE`. Все системные промпты DWF написаны
на английском. Профиль хранит версии промптов и содержимого скиллов
отдельно, чтобы обновление скилла сохраняло доступ к версии прежней сессии.

## Запуск первого сценария

### Настройки участников и управление

Настройки в `roles` наследуются узлами соответствующей роли. Узел может
переопределить `model`, `reasoning`, `tools`, `skills` и `memory`. Списки
заменяются целиком. Пустой список отключает инструменты или скиллы.
`reasoning: null` отключает выбор варианта модели. `memory: false` создаёт
новую сессию при следующем обычном посещении. По умолчанию история сохраняется.
Выбранная конфигурация и версии системных инструкций сохраняются с запуском.

```json
{
  "task": "Проанализировать документы проекта",
  "workspace": "directory",
  "entry": "review",
  "roles": {"reviewer": {"tools": ["read", "glob", "grep"], "skills": []}},
  "nodes": {"review": {"role": "reviewer", "memory": true}},
  "transitions": {"review": {"approve": null, "changes": null}}
}
```

`workspace: "directory"` использует текущий каталог для read-only ролей,
в том числе вне Git. Снимок файлов контролирует их сохранность. Обычный режим
`worktree` создаёт изолированное рабочее дерево для разработки.
Интеграция требует актуального одобрения каждого обязательного reviewer и
verifier. Эти участники обязательны по умолчанию. `required: false` делает
конкретного проверяющего консультативным. Отрицательный итог обязательной
проверки препятствует успешному завершению и при `merge: false`.

```sh
dwf steer <runId> <node> --message-file /tmp/refinement.txt
dwf stop <runId>
```

Уточнение сохраняется до доставки на границе ответа выбранного участника.
Повторное посещение для уточнения использует его прежнюю сессию. Остановка
прерывает сессии и команды запуска, сохраняет историю и возвращает `cancelled`.
Повторная остановка возвращает то же состояние. Приём команд и переход к
завершению сериализованы, поэтому принятое уточнение или остановка учитываются
до интеграции.

### Параллельные группы

В `groups` можно задать `{"members":["first","second"]}` для одновременного
запуска существующих узлов. Группа имеет переходы `done`, `changes`, `failed`
и передаёт следующему узлу все результаты с идентификаторами источников.
Ошибки ветвей сохраняются. `required` задаёт обязательное подмножество участников,
по умолчанию обязательны все.

Форма `{"member":"worker","itemsFrom":"planner"}` создаёт участников по
массиву `items` из результата указанного узла. Также можно задать `items` прямо
в группе. Элементы имеют уникальные `id`, отдельные сессии и адреса
`groupName/itemId` для steering. Результаты уже завершённых ветвей используются
при восстановлении контроллера.

Писатели получают отдельные рабочие деревья. Успешные изменения объединяются
перед следующим узлом, а конфликт сохраняет исходное дерево группы и результаты
ветвей. Общее ревью и верификацию размещай после объединения. Пример полного
графа находится в инструкции CLI скилла `dwf-oc`.

### Обычная разработка

Нужны macOS или Linux, Node 22.19+/24/26+ и npm. Установка локальная.

```sh
npm ci
# Из каталога целевого Git-проекта с чистой исходной веткой
dwf schema
dwf start --file /tmp/workflow.json
dwf inspect <runId>
dwf inspect <runId> --watch
```

Команда `dwf` здесь установлена в PATH. Агент составляет workflow под поручение.
DWF создаёт отдельную ветку и рабочее дерево, исполняет заданные переходы.
Рабочее дерево сохраняется по пути из `inspect`. При включённом merge исходная
ветка должна оставаться чистой и на прежнем коммите до интеграции.

Для собственного workflow используй `dwf schema`, сохрани поля `task`, `entry`,
`nodes`, `transitions` и необязательное `merge` во временный JSON вне проекта.
`dwf start --file /tmp/workflow.json` запускает схему. Переход `null` завершает её.
Обычно узлам достаточно `role`. Общую задачу и критерии записывай в `task`.
Необязательные `instructions` нужны для особой области работы участника.
Роли уже получают свои системные промпты, скиллы и формат завершения.
Результаты worker и
orchestrator — `done`, reviewer и verifier — `approve` или `changes`.
`dwf preset save my-workflow --file /tmp/workflow.json` сохраняет пресет,
`dwf preset list` показывает доступные имена. При запуске пресета новый
`--task-file` заменяет поручение, сохраняя роли и переходы.

Старый формат `{"planner":{"task":"поручение"}}` продолжает работать.

Установка выполняет штатный postinstall OpenCode для выбора и подключения
бинарного файла своей платформы.

`start` возвращает JSON с `runId` после сохранения и принятия поручения.
`inspect` возвращает `running`, `succeeded` с `result` или `failed`
с причиной. Для workflow доступны `current`, `history`, `workspace` и итоговый
`result.commit` после merge. Для старого планнера `result` содержит точный текст.
Недоступность сервиса сообщается отдельным полем `service` и сама
по себе не превращает поручение в окончательно неудачное.

`dwf inspect <runId> --watch` выдаёт события отдельными JSON-строками. Первое и
последнее события имеют `type: "snapshot"` и полное состояние в поле `state`.
Между ними события `type: "update"` передают только изменившиеся поля в `changes`.
`removed` перечисляет удалённые поля, `historyUpdates` заменяет или добавляет
изменившиеся посещения по нулевому `index`, передавая запись в `entry`.
Неизменившиеся отчёты этапов повторно не передаются. Закрытие наблюдателя сохраняет независимое
исполнение workflow. `current.startedAt` показывает начало этапа,
`current.progress.updatedAt` — последнюю активность в Unix ms. Прогресс содержит
видимое промежуточное `message`, последние `tools` с их состояниями и сведения
о штатном повторе запроса `retry`, когда они доступны. Он сохраняется в SQLite
и доступен при повторном подключении.

После merge `result.integration` подтверждает состояние `merged`, ветку и коммит.
Итоговый `summary` начинается с фактического результата интеграции DWF, после
которого идёт отчёт участника, подготовленный до слияния. Это отображение применяется
и к ранее завершённым workflow.

Родительские `AGENTS.md` исходного проекта сохраняются при запуске и передаются
участникам вместе с путём рабочего дерева. Инструкции внутри проекта участники
читают из рабочего дерева. Вычислением снимков и соответствием одобрений текущим
файлам управляет DWF.

Сохранённый окончательный результат доступен без работающего OpenCode.
Для уточнения незавершённого состояния `inspect` при необходимости поднимает
общий сервис. Его запуск может возобновить другие незавершённые поручения
согласно штатной ограниченной политике OpenCode. Обрывы по длине также
обрабатываются штатно. После успешного продолжения текст всех частей
читается в исходном порядке. Аварийно остановленный контроллер workflow
восстанавливается через `inspect` после истечения его 30-секундной аренды.

| Настройка | Назначение |
| --- | --- |
| `DWF_STATE_DIR` | Абсолютный корень состояния вне рабочего проекта, по умолчанию `~/.dwf` |
| `DWF_PLANNER_MODEL` | JSON с `provider` и `modelId`, по умолчанию `openai/gpt-6.1-sol-ultrafast` |
| `DWF_PLANNER_REASONING` | Уровень рассуждения, по умолчанию `high` |
| `OPENCODE_CONFIG` / `OPENCODE_CONFIG_CONTENT` | Штатная конфигурация OpenCode при первичной настройке собственного сервиса |

DWF сохраняет связи запусков и принятые результаты в `<state>/dwf.sqlite`.
Собственный OpenCode размещает профиль, регистрацию сервиса и native БД в
`<state>/opencode/`. Личный стандартный профиль OpenCode обслуживается отдельно.
Переданная при первичной настройке конфигурация сохраняется для восстановления
после выхода исходного клиента. Несовместимая версия сервиса требует явного
обновления.

## Штатная авторизация OpenCode

В этой сессии собственный профиль DWF авторизован пользователем. Для настройки
нового корня сначала создаётся сервис DWF, затем вызывается штатный login
OpenCode в его пространстве регистрации.

```sh
export DWF_STATE_DIR="${DWF_STATE_DIR:-$HOME/.dwf}"
node --input-type=module -e 'import {connect} from "./opencode-runtime.mjs"; await connect(process.env.DWF_STATE_DIR)'
OPENCODE_CONFIG_DIR="$DWF_STATE_DIR/opencode/config" \
XDG_STATE_HOME="$DWF_STATE_DIR/opencode/state" \
./node_modules/.bin/opencode auth login openai
```

Управляемые проверки используют локальную модель без секретов. Настоящий прогон
использует собственный авторизованный профиль DWF, сохраняет обычный модельный
транспорт и добавляет временный нативный наблюдатель OpenCode. В отчёты попадают
параметры модели и текст ответа. Заголовки авторизации и токены туда не пишутся.

## Проверки

```sh
npm test
npm run test:steps
DWF_TEST_REAL_STATE_DIR=/absolute/path/to/authorized-dwf-state \
DWF_PLANNER_MODEL='{"provider":"openai","modelId":"gpt-6.1-sol-ultrafast"}' \
npm run test:real
```

`npm test` исполняет самопроверки, тесты хранения и Git-интеграции, исходный
controlled-сценарий, сценарии восстановления, продолжения по длине,
параллельных запусков и циклов reviewer/verifier с сохранением сессий.
`test:steps` проверяет только привязку шагов. Для `test:real` нужен отдельный
авторизованный профиль с остановленным сервисом. Приёмка сама запускает его,
проверяет результат после остановки и удаляет свой временный наблюдатель.
Текущие отчёты — в `acceptance-results/opencode/`; прежние отчёты сохранены отдельно.

Интерактивный `attach` ещё не реализован. Ранее согласованные свойства доступа
к живому участнику остаются следующим этапом.

Для ручной работы с установленной здесь версией OpenCode из каталога проекта
можно задать короткую команду на время текущего терминала.

```sh
alias opencode="$PWD/node_modules/.bin/opencode"
opencode
```

### Независимый тестер

Запускатель создаёт свежую сессию обычного OpenCode build, загружает только каталог
скилла `dwf-oc` и передаёт содержимое файла как пользовательское поручение.
Тестер сам составляет workflow и запускает публичный `dwf`. Для каждой пробы
создаётся отдельная Git-копия чистой исходной ревизии, в которую DWF затем
интегрирует результат. Исходный стенд сохраняется для повторения той же задачи.

```sh
node acceptance/tester.mjs start --project /path/to/project --prompt-file /tmp/task.txt
node acceptance/tester.mjs inspect /path/printed/as/attempt --watch
```

`start` печатает путь пробы и наблюдает до итогового ответа. Если наблюдение
оборвалось, `inspect --watch` подключается к сохранённой сессии с тем же ID ввода.
Без `--watch` он возвращает текущее состояние. Завершение сессии тестера ещё
требует проверки его отчёта и фактического состояния запущенного им workflow.

По умолчанию пробы находятся в `~/.dwf/tester/attempts/`. `DWF_STATE_DIR` задаёт
другой корень DWF. В каждой пробе сохраняются `attempt.json`, `prompt.txt`,
`skills.json`, видимые сообщения и вызовы инструментов в `messages.json`,
`state.json` и окончательный `report.md`. Личная цепочка рассуждений исключается
из журнала. Тестер использует GPT-6.1 Sol Ultrafast с reasoning high.

У тестера отдельный сервис и база OpenCode. При первом запуске существующий
вход DWF передаётся через штатный экспорт и API учётных данных OpenCode.
Учётные данные хранятся в закрытом профиле, журнал пробы их не содержит.

### Изолированные испытания с закрытым эталоном

`node acceptance/benchmark.mjs /private/path/case.json` запускает пробу
с проверкой границ macOS sandbox-exec. Файл настройки находится в контуре
проверяющего и задаёт `root`, `project`, `baseline`, `prompt`, при необходимости
`runtimeRevision`, `readable`, `copy`, `environment`, `hidden`.

```json
{
  "root": "/private/evaluation/series",
  "project": "/private/evaluation/upstream",
  "baseline": "commit-before-the-change",
  "prompt": "Реализуй описанное поведение через DWF.",
  "readable": ["/private/evaluation/toolchain"],
  "environment": {"GOCACHE": "{{attempt}}/go-cache"},
  "hidden": ["/private/evaluation/hidden-check.txt"]
}
```

Каждая проба получает один исходный Git-коммит, отдельные каталоги состояния
и зафиксированную копию исполняемого DWF и скилла. История исходного репозитория,
записи задач DWF и материалы прошлых проб остаются за границей доступа.
`copy` принимает массив объектов `from` и `to`, где `to` относителен каталогу
пробы. Так можно подготовить автономный кеш объявленных зависимостей.
Сетевые запросы модели проходят через прокси с ограниченным списком адресов.
Доступ к другим адресам и к соседнему локальному сервису проверяется перед
запуском. `hidden` перечисляет существующие файлы, чтение которых должно
отклоняться. Проверка границ, происхождение исходников, версии и журналы
сохраняются в закрытом `root`. Приёмку готового результата выполняют отдельно.

смерти финальное состояние читается повторно, чтобы исключить гонку завершения.

## Видение и решения интервью

Это согласованные ориентиры продукта, а не объём первой реализации. Первый
законченный сценарий остаётся прежним: один планнер через pi, независимый от
запустившего его CLI, с последующим получением сохранённого результата.

- Внешний агент собирает workflow из готовых примитивов и блоков через инструмент
  или декларативное описание. Ему не требуется писать программу оркестрации.
  Начальные роли: кодер, ревьюер, планнер, оркестратор. Главный внутри workflow
  необязателен. Блок объединяет несколько примитивов, например четырёх ревьюеров.
- У примитива настраиваются модель, reasoning, инструменты и скиллы. Новый
  примитив сначала отдельно создаётся и согласовывается. Базовые инструкции
  существующей роли сохраняются; специализация задаётся инструкциями задачи.
  Полная замена базового промпта возможна для одного запуска после согласования
  с постановщиком задачи. Библиотека при этом не меняется; обязательный формат
  результата роли сохраняется.
- Технически успешное выполнение и содержательный вердикт различаются. Ревьюер
  может успешно вернуть отрицательный вердикт с объяснением. Дальнейший путь
  задаёт схема: завершение либо цикл исправлений. Отсутствующий обязательный
  вердикт — ошибка формата, а не повод угадывать решение. В обсуждавшемся блоке
  единогласного ревью одного отрицательного вердикта достаточно для отказа.
- У всех примитивов по умолчанию `memory: true`: повторные поручения тому же
  участнику в одном запуске продолжают его сессию. При `false` следующее поручение
  начинает новую сессию с инструкциями роли и явно переданными входами. Внутри
  текущего поручения контекст сохраняется, включая steering. История старых
  сессий доступна пользователю. Участники не делят память; новый запуск пресета
  начинает новые истории. Продление прежнего запуска сохраняет его состояние.
- Получатель видит своё поручение, исходные требования, итоговые результаты
  предшественников и явно приложенные материалы. Полные чужие переписки
  автоматически не передаются. Ответ возвращается выдавшему это поручение:
  например, после «кодер → главный → ревьюер» результат получает главный.
- Зависимости, параллельные группы, ветвления и циклы задаёт внешний сборщик.
  Итоги группы приходят получателю одним подписанным набором после завершения
  всех обязательных участников. Система не определяет по смыслу, одинаковы ли
  задания: независимые проверки одного объекта могут быть намеренными.
- Вопрос участника может поступить адресату до завершения всей группы, не запуская
  итоговое сведение результатов. Вопросы агентов ожидают очереди и не прерывают
  текущую работу адресата. При необходимости решения виден статус ожидания;
  независимые ветви продолжаются. Ответ позволяет продолжить ту же сессию.
- Внутренние участники не меняют структуру workflow, включая число исполнителей.
  Внешний уполномоченный агент может явно изменить текущий запуск с сохранением
  состояния и истории; пользователь может поручить это другому внешнему агенту.
  Автоматическое обновление библиотеки не меняет настройки уже запущенного
  workflow, включая ещё не начавших работу участников.
- Изменения структуры ожидаются редко. При добавлении пятого участника в ещё
  не переданную группу получатель ждёт всех пятерых. Завершённую группу можно
  открыть снова: получатель заканчивает текущую работу по прежним четырём ответам,
  затем после пятого получает дополнительное поручение пересмотреть результат.
- Запустивший агент может уйти и больше не вернуться. Пользователь должен видеть
  схему, текущий этап, работающих участников и их реальные поручения. Он может
  войти в сессию выбранного участника и прервать текущую работу новой инструкцией
  с сохранением контекста. Steering касается только этого участника.
  Уточнение Q27: интерфейс по запросу подключается к реальному разговору,
  показывает историю, текущий незавершённый ответ и работу инструментов.
  Новая инструкция адресуется той же сессии; закрытие окна отключает просмотр,
  сохраняя исполнение. Допустима интеграция интерфейса на компонентах pi.
  Просмотр логов или второй исполнитель по копии истории этого не обеспечивают.

### Что не повторять

| Антипаттерн | Почему плохо и как заметить возвращение |
| --- | --- |
| Исполнение расходится со схемой | Независимые задания идут последовательно или получатель обрабатывает неполную группу; это видно по событиям запуска и передачи результатов. |
| Контекст теряется или смешивается | При `memory: true` продолжение получает новую историю либо участник видит чужую историю без явной передачи. Одного совпадения имени участника недостаточно для проверки. |
| Скрыто меняется смысл роли | Разовая сборка переписывает базовый промпт без согласования, меняет обязательный результат или затрагивает библиотеку и другие запуски. |
| Наблюдаемость существует отдельно от исполнения | Схема показывает этап, но нельзя связать его с реальным поручением, сессией и результатом. |
| Окно управляет жизнью агента | Открытие создаёт второго исполнителя, переключение теряет контекст или закрытие окна останавливает работу. Проверяем адресацию к прежней сессии и продолжение после отключения интерфейса. |
| Число окон и процессов автоматически равно числу агентов | Для доступа к одному участнику постоянно держатся терминалы всех остальных. Число интерфейсов должно зависеть от просмотра; размещение исполнителей выбирается отдельно с учётом нагрузки. |
| Тесты подтверждают собственные заготовки | `.feature` не запускается, шаг пуст, заменён сам движок либо успех проверяет только заранее заданный ответ. Нужны реальные CLI/сохранение и отдельно настоящий pi. |
| Ожидания подгоняются под реализацию | Реализатор меняет или отключает приёмку без отдельного разбора требования. Техническую невозможность запуска называют содержательным RED. |

Работа идёт по одному сценарию: согласованное поведение → исполняемая падающая
приёмка → реализация отдельным агентом → проверка. Для первоначально пустого
проекта отдельно принято исключение: отсутствие CLI — технический блокер;
после реализации силу теста нужно показать целевой поломкой и восстановлением.
Область видимости файлов, конкретное оформление и реализация интерфейса,
восстановление после обрыва ответа пока не согласованы. Поведение подключения
к живой сессии согласовано в Q27. Остальные возможности выше не добавляются
в первый сценарий автоматически.

**Q32, согласовано 2026-10-10:** следующим небольшим сценарием выбрано
подключение к работающему планнеру и steering: просмотр живого разговора,
уточнение в той же сессии и продолжение работы после закрытия интерфейса.
Первую параллельную группу сейчас не реализуем. Перед новой приёмкой уточняем
конкретный пользовательский пример и недостающие договорённости о результате;
выбор этого шага сам по себе не утверждает UI или транспорт.

**Q33, согласовано 2026-10-10:** уточнение во время работы продолжает то же
поручение в том же запуске и разговоре. Прерывание текущего ответа из-за steering
само по себе не переводит workflow в `failed`: работа продолжается. Итоговый
`result` — законченный план с учётом уточнения. Прерванный черновик доступен
в истории, но готовым результатом не считается. Это договорённость следующего
сценария; текущая реализация ещё не поддерживает steering.

Конкретный согласованный пример: планнер продумывает уведомления в приложении,
пользователь видит проработку email и SMS и уточняет: «В первой версии только
email, SMS исключи». Готовый план этого запуска должен учитывать уточнение.

**Q34, согласовано 2026-10-10, вариант 1:** если планнер успел завершить
поручение перед отправкой уточнения, сообщение принимается как продолжение
того же разговора с прежним контекстом. Тот же запуск снова становится
работающим; после доработки его результатом становится новый законченный план.
Пользователю не нужно успевать отправить сообщение до окончания генерации.
Способ возобновления исполнения этим ответом не выбран. Поведение последующих
узлов произвольного графа здесь не согласовывалось: пример относится к одному

[pi-ai transform](https://github.com/earendil-works/pi/blob/v1.0.2/packages/ai/src/api/transform-messages.ts),

Это кандидат для управляемого опыта, пока не проверенный исполнением.
Снимок после отмены может содержать ещё не показанный текст, поэтому он сам
по себе не доказывает сохранение именно виденного пользователем фрагмента.

`fa224ac88b88e7044502848bce58337e98c9dc5df4b0ecb76b92317d33141edb`.
Все 11 файлов сверены 2026-11-07, самопроверка harness дала 9/9 PASS,
dry-run связал 1 сценарий / 13 шагов. Эти проверки подтверждают готовность
приёмки, продуктовый перенос ими пока не проверен.

Минимальный план к рассмотрению: кандидат для bootstrap — штатные
discovery/health/start через `Service.ensure` с совместимой версией, командой
запуска и согласованным registration namespace; новый supervisor не писать.
Путь registration у клиента должен совпадать с путём, вычисляемым namespace
запущенного сервера; сменить только клиентский `file` недостаточно.
`ensure(version)` может заменить несовместимый общий сервис, поэтому это нельзя
считать простым чтением или молча разрешённым обновлением всех workflow.
Поведение запуска сервиса из `inspect` утверждено в Q44. `start --file`
сохраняет адресацию `runId → sessionId + inputId` до отправки, ждёт долговечного
подтверждения admission и возвращает `runId`, после чего клиент выходит.
Повтор отправки допускается только с прежними ID и тем же поручением.
Запись принадлежит SQLite DWF по Q41; конкретная схема и размещение остаются
деталями реализации в пределах принятого разделения. Auth-профиль этим не выбран.
`inspect` читает публичную сохранённую историю: конкретный input, его завершённый
интервал до idle и относящийся к нему нормально законченный ответ. Последний
assistant всей session не является универсальной адресацией результата.
Первый шаг покрывает одно поручение планнеру в новой session; attach и обновление актуального
результата при человеческих продолжениях требуют следующего сценария.
Внешняя приёмка должна подтвердить выход caller, параметры реального запроса,
точный результат из другого клиента и повторное чтение без модельного вызова.
Принятому в Q40 восстановлению соответствует штатный managed-сервис;
обычный `serve` не включает такой sweep автоматически. Конкретные настройки
bootstrap, хранения и совместимости версии ещё требуют технического плана.

### Пример согласованного поведения подключения, Q27

Исторический черновик ниже описывает немедленное прерывание. После разрешённого
в Q38 steering на границе шага этот пункт требует уточнения перед новой приёмкой;
точный контракт attach по-прежнему не выбран.

Это описание для последующей исполняемой приёмки; пока оно не добавлено в
`.feature` и не считается выполненным тестом. Основание — прямое согласие
пользователя с последовательностью выбора, просмотра, уточнения и отключения.

```gherkin
Scenario: Пользователь вмешивается в работу участника через подключаемый интерфейс
  Given два участника workflow работают в своих отдельных разговорах
  When пользователь открывает первого участника посреди его ответа
  Then интерфейс показывает его историю и текущий незавершённый ответ
  When пользователь отправляет новую инструкцию
  Then она прерывает текущую работу первого участника и поступает в тот же разговор
    And прежний контекст первого участника сохраняется
    And второй участник продолжает своё поручение без этой инструкции
  When пользователь закрывает окно первого участника
  Then первый участник продолжает работу с учётом новой инструкции
```

Сценарий должен ловить подключение к копии истории вместо живого разговора,
ошибочную адресацию steering и зависимость исполнения от открытого окна.
Совпадения имени участника недостаточно: будущая проверка должна наблюдать
фактическое получение инструкции, сохранение контекста и продолжение работы.
Штатный `whenBusy: "steer"` Durable ждёт границы инструментов; сам по себе
он не доказывает ранее согласованное прерывание. В отдельном опыте ниже
проверена последовательность отмена → подтверждённый простой → новое поручение.
Это пока не исполняемая приёмка продукта.

### Пример согласованного поведения после сохранения ответа, Q29

```gherkin
Scenario: Сохранённый план доступен после падения исполнителя до объявления успеха
  Given полный ответ планнера нормально завершён и сохранён в Durable
    And DWF ещё не объявил успешное завершение запуска
  When процесс исполнения аварийно завершается
    And новый клиент запрашивает результат этого запуска через CLI
  Then клиент получает статус succeeded и точный сохранённый ответ

```

Основание — выбор пользователем варианта 1 в Q29. Сценарий ловит потерю доступа

## Запуск

Нужны macOS или Linux с `ps`, Node 22.19+/24/26+ и npm. В devDependencies
закреплены `@cucumber/cucumber` 13.2.1 и `@earendil-works/pi-ai`,
`@earendil-works/pi-durable`, `@earendil-works/chord` версии 1.0.2; обновлён lockfile.
pi-ai нужен обоим провайдерам; Durable и chord используются в самопроверке
подключения к настоящим Harness и SQLite. Глобальный `pi` тестам больше не нужен.

```sh
npm ci --ignore-scripts
npm run test:harness
npm run test:steps
npm run test:acceptance
npm run test:pi
```

`test:steps` — только dry-run: проверяет нахождение сценариев и привязку всех шагов.
Это не исполнение приёмки. `.feature` действительно исполняется командами
`test:acceptance` и `test:pi`. `npm test` запускает самопроверку harness и основную
приёмку; настоящий pi вынесен в явную отдельную команду, поскольку требует
настроенного провайдера и обращения к модели. В шагах нет pending/undefined,
ручных skip или возврата успешной приёмки при отсутствии продукта.

По умолчанию запускается настоящий `dwf` из PATH; локальный `node_modules/.bin`
имеет приоритет. Если будущий CLI запускается иначе, передайте argv без оболочки:

```sh
DWF_TEST_CLI='["node","/absolute/path/to/real-dwf-cli.mjs"]' npm run test:acceptance
```

Указать нужно реальный продуктовый entry point. Создание фиктивного `dwf` для
прохождения сценария недопустимо. Другой клиент — новый процесс того же CLI,
с тем же каталогом состояния, а не внутренний вызов функций продукта.

JSON-отчёты: `acceptance-results/controlled.json` и `acceptance-results/pi.json`.
В них сохраняются код/сигнал выхода и PID клиентов, независимые свидетельства
модельного провайдера и текст плана для отдельного человеческого ревью.
Сырые stdout/stderr, API-ключи, headers, полное окружение и payload не публикуются.
Форматтер пишет эти файлы даже при падении сценария. Временный проект, состояния
и процессы убирает `After` в `finally`; исходники и зависимости тестов остаются.

## Согласованный контракт первого CLI

В ответе Q21 пользователь согласовал вход `planner.task`, команду `start` с
немедленным возвратом `runId` и выходом клиента, команду `inspect` с `runId` и
`status`, а также итоговый ответ `status: "succeeded"` с точным текстом в `result`.
Это контракт первого сценария; будущий формат графа ещё предстоит согласовать.
Дополнительные поля ответов тестами не запрещаются.

Файл workflow:

```json
{"planner":{"task":"Текст поручения и переданное описание dynamicwf"}}
```

Планнер ровно один. Нет графа, рецептов, других ролей, зависимостей между узлами
или универсальной системы расширений.

Успешный ответ `dwf start --file workflow.json`:

```json
{"runId":"opaque-nonempty-id"}
```

`runId` — непрозрачная непустая строка; тест не требует UUID, определённой длины
или формата. Успешный вызов завершается с кодом 0 и одним JSON-объектом на stdout;
диагностика может идти в stderr.

Пример промежуточного состояния и согласованный итоговый ответ
`dwf inspect <run-id>`:

```json
{"runId":"opaque-nonempty-id","status":"running"}
```

```json
{"runId":"opaque-nonempty-id","status":"succeeded","result":"Текст исполнителя"}
```

Имя `succeeded` согласовано для технического успеха. В Q28 согласовано `failed`
с понятной причиной при окончательной ошибке планнера или обрыве по лимиту;
готового `result` в таком исходе нет, новый запуск автоматически не создаётся.
Тест не закрепляет конкретное имя промежуточного состояния: до разрешения он
проверяет отсутствие успеха и готового результата. `result` до готовности может
отсутствовать или быть `null`. После успеха это точный текст итогового ответа,
без перефразирования. Текстовые блоки одного итогового сообщения соединяются
в исходном порядке без добавленных разделителей и без удаления пробелов.
Это локальная сериализация точного текста; нетекстовые блоки в `result` не входят.
Форматы ошибок, неверные входы и неизвестные идентификаторы здесь не проектируются.

## Управляемый модельный провайдер

`controlled-provider.mjs` экспортирует согласованную фабрику
`createProvider({ baseProvider })`. Она возвращает штатный pi-ai `fauxProvider`
с ID `dwf-acceptance` и моделью `planner`. Подменяются только ответы модели:
CLI, Durable, исполнение и постоянное хранение обязан предоставить продукт.
Старые `controlled-pi.mjs`, `observe-pi.mjs` и настройка их RPC-команд удалены.

Продукт принимает три согласованные настройки `DWF_STATE_DIR`,
`DWF_PLANNER_MODEL`, `DWF_MODEL_PROVIDER_MODULE`; точная таблица обязанностей
находится ниже в разделе «Согласованные настройки продукта». Формат workflow
одинаков для обоих прогонов. Продукт не читает сигналы/свидетельства теста и
получает результат только из модельного потока.

Модуль пишет в закрытый временный `control/provider.jsonl` разрешённые записи:
`received` (сигнал готовности с фактическим user-поручением, хешами, callId,
provider session ID, PID/UID/временем рождения), затем ждёт `release.json` с
совпадающими token и callId. После разрешения появляются `generated` с новым
nonce и хешем фактического поручения и `completed` с точным терминальным текстом
и stopReason. Полные сообщения не сохраняются, только их хеш и user-поручение.
Чтение принимает лишь полностью записанные строки, завершённые LF; U+2028/U+2029
не являются границами записей. Отмена передаётся штатному fauxProvider.

Порядок доказывается событиями и сигналами:

1. Настоящий `start` запускается отдельным процессом.
2. Тест наблюдает его `exit` с кодом 0, закрытие потоков и JSON с runId.
3. До разрешения тест сверяет `received`, убеждается, что первоначальный процесс
   жив, и отдельным `inspect` проверяет отсутствие успеха и готового результата.
   После `inspect` исходная идентичность процесса проверяется снова.
4. Только затем тест создаёт `release` для этого вызова.
5. Новые процессы `inspect` получают успех того же runId и точный ответ с nonce,
   возникшим у провайдера после разрешения. До терминального свидетельства
   проверяется жизнь первоначального процесса; дополнительный вызов модели
   не может скрыть его прекращение.
6. Harness останавливает процессы теста, сохраняя данные; ещё один новый
   `inspect` возвращает тот же результат без нового модельного исполнения.

Опрос ждёт наблюдаемые сигналы; истечение задержки не считается готовностью.
Таймауты защищают тест от зависания и не являются SLA продукта:
`DWF_TEST_START_TIMEOUT_MS=15000`, `DWF_TEST_READY_TIMEOUT_MS=15000`,
`DWF_TEST_RESULT_TIMEOUT_MS=20000`, `DWF_TEST_PI_TIMEOUT_MS=180000`.
Очистка проверяет UID, уникальную наследуемую метку `DWF_ACCEPTANCE_TOKEN`, PID
и время рождения перед каждым сигналом, включая отделившихся потомков.
Сначала SIGTERM, ограниченное ожидание и при необходимости SIGKILL; удаляется
только корень этого теста после остановки процессов. Пользовательские сессии,
авторизация и настройки не изменяются. Самопроверка подтверждает очистку при
исключении, сохранность чужого процесса и отказ принимать другую идентичность.

## Интеграция с настоящей моделью через Pi Durable

Запуск требует явной пары штатного provider/modelId и выбранного источника
авторизации. Изначально поддерживалось только окружение; 2026-10-10 согласован
также существующий вход pi, его подключение описано ниже. Для API-авторизации:

```sh
DWF_PLANNER_MODEL='{"provider":"YOUR_PROVIDER","modelId":"YOUR_MODEL"}' npm run test:pi
```

Значения в примере — placeholders, их нужно заменить настоящей моделью.
Секрет передаётся предусмотренной провайдером переменной окружения; его значение
не включается в команду-пример, свидетельства или отчёт. В режиме окружения тест
проверяет выбор в каталоге pi-ai 1.0.2 и доступность авторизации, используя
in-memory stores и authContext без доступа к пользовательским файлам.
Для явно выбранного режима pi предусмотрена штатная проверка `pi auth check`
без вывода credentials. При необходимости штатный
SDK обновляет каталог только выбранного провайдера, с ограниченным ожиданием.
Отсутствие настройки,
модели или авторизации — явное техническое препятствие, без skip/fallback.

`observe-provider.mjs` прозрачно вызывает штатный Provider с его `this`, моделью,
сообщениями и параметрами. `streamSimple` синхронно возвращает тот же
AssistantMessageEventStream; независимый наблюдатель использует только result(),
без второго потребителя событий. Остальные методы, отмена и callbacks сохраняются.
Обёртка onPayload возвращает прежний результат callback (включая заменённый
payload и undefined) и записывает только разрешённые числовые поля лимита.

Свидетельства связывают фактически полученное поручение, вызов, выбранную модель
и терминальный ответ. Проверка требует у последнего итогового ответа именно
`stopReason: "stop"`: непустой `length`, `error`, `aborted` или `toolUse` не
доказывает готовый план. Статус submission Durable этого не заменяет. Итоговый
текст сравнивается с результатом CLI точно, включая пробелы, переводы строк и
U+2028/U+2029; после остановки процессов повторяется чтение через новый inspect.
Поручение планнеру описывает согласованный сценарий через Durable, без требования RPC.

Максимум ответа вычисляется штатной функцией clampMaxTokensToContext pi-ai 1.0.2
на фактическом контексте и model.maxTokens. Переданный продуктом maxTokens может
равняться model.maxTokens или уже ограниченному контекстом максимуму; меньший
произвольный и превышающий максимум лимиты отвергаются. Через onPayload сверяется
фактический числовой лимит. Учтён штатный минимум 16 для OpenAI Responses и
отсутствие поля лимита у Codex Responses 1.0.2. Неизвестное поле лимита или
отсутствие onPayload — техническое препятствие наблюдения, не успешная проверка.
Сами запросы и ограничения наблюдатель не изменяет.
Источник: [штатный расчёт лимита 1.0.2](https://github.com/earendil-works/pi/blob/v1.0.2/packages/ai/src/api/simple-options.ts).

Управляемый прогон проверяет механику, причинный порядок, доставку и сохранение.
Он не доказывает работу настоящей модели и её авторизации: для этого нужен
отдельный test:pi. Лог dwf и непустой result недостаточны для происхождения
ответа. Заголовки/ключевые слова не проверяются; полезность плана оценивает человек.
Итог при окончательной ошибке и обрыве определён в Q28; потеря исполнителя до
сохранения — в Q30. Продолжение и восстановление остаются вне первого сценария.

## Проверка силы теста конкретной поломкой

**Пока не выполнена: реализация отсутствует.** Подготовлен проверяющий скрипт
`verify-lifetime-mutation.mjs`, который запускает тот же `.feature` и проверяет
причину падения. Он не редактирует продукт и не создаёт продуктовую заглушку.

После появления работающей реализации выполнить три фазы:

1. `npm run test:mutation -- before`: неизменённый основной сценарий обязан пройти.
2. Временно изменить **продуктовый start**: дождаться записи `received` от
   управляемого провайдера, вернуть штатный runId/код 0 и связать выход клиента
   с прекращением именно удержанного процесса из identity этой записи.
   Для воспроизводимой мутации в обработчике завершения start подтвердить
   прекращение исполнителя перед нормальным выходом клиента.
   SIGTERM/SIGKILL допустимы только после проверки
   принадлежности PID/UID/времени рождения данному тесту. Чтение свидетельства
   и такая связь допустимы исключительно во временной мутации и затем удаляются.
3. `npm run test:mutation -- broken`: нужен `LIFETIME_FAILURE` от проверки
   первоначального процесса при успешно завершившемся start. В отчёте должны
   остаться фактическое получение поручения, совпадающая identity и отсутствие
   терминального ответа. Падение возможно до разрешения или при ожидании ответа;
   исходный процесс проверяется до и после inspect, поэтому запуск замены
   не скрывает прекращение незавершённой работы. After обязан пройти.
   ENOENT, импорт, синтаксис, произвольное падение и один таймаут не засчитываются.
4. Удалить временную поломку и выполнить `npm run test:mutation -- after`:
   неизменённая приёмка должна снова пройти.

Скрипт сохраняет отчёты и свидетельства фаз в acceptance-results/mutation-*,
сверяет хеш тестовых файлов, конфигурации, package/lockfile и команды CLI между
фазами; отвергает пропуски в зелёных прогонах. Самопроверка проверяет распознавание
конкретной причины и отказ засчитывать технические сбои. Она не является
экспериментом с продуктом. Временную правку продукта нужно показать ревьюеру.
Трёхфазный эксперимент пока не выполнен: реализации нет.

### Хранение и Pi Durable: обсуждение после релиза

Пользователь предложил `~/.dwf/` как основной каталог данных. Выбор конкретного

Проверенные источники: [Node SQLite](https://nodejs.org/download/release/v26.8.2/docs/api/sqlite.html),
[когда подходит SQLite](https://www.sqlite.org/whentouse.html).

Вместе с pi 1.0 выпущен отдельный **экспериментальный** `@earendil-works/pi-durable`
(проверенная версия 1.0.2). Он исследован по документации и исходникам,
а после выбора в Q24 установлен в devDependencies для подготовки приёмки.

Библиотека предоставляет постоянные conversations, очереди, checkpoints задач,
возобновление, параллельное исполнение и наблюдение. SQLite-backend использует
`node:sqlite`. Хранилищем владеет один процесс; готового CLI/демона нет.
Структура workflow, правила примитивов, внешний интерфейс и время жизни владельца
остаются задачами dynamicwf. `steer` ждёт завершения текущего раунда tools;
вариант abort → submit в ту же conversation требует проверки последствий для
очереди и дочерних задач. Live task graph библиотеки не является полной схемой
workflow с завершёнными и будущими этапами.

## Договорённость о длине ответа

Для первого шага используем максимально допустимую длину ответа выбранной модели
с учётом доступного контекста. Dynamicwf не вводит собственный уменьшенный лимит
и не подставляет произвольное огромное число сверх возможностей модели/провайдера.
В проверенном штатном пути pi 0.85.0 и 1.0.2 при отсутствии явного ограничения используются
`model.maxTokens` и ограничение по оставшемуся контексту; отдельная настройка
dynamicwf для этого пока не нужна. При интеграции нужно проверить, что этот
максимум не уменьшается дополнительными настройками запуска.

Это решение о запрашиваемой длине ответа, а не гарантия отсутствия обрывов.
Впоследствии в Q28 согласован исход `stopReason: "length"`: `failed` с понятной
причиной, без готового результата и автоматического нового запуска. Увеличение
лимита само по себе не исключает этот исход. Ручное продолжение и восстановление
незавершённой работы остаются за пределами первого сценария.

## Согласованное подключение провайдера для Durable, 2026-10-06

**Согласовано пользователем в Q25; тестовые файлы адаптированы 2026-10-06.**
Утверждено техническое подключение для первого сценария; внешний CLI-контракт сохранён.
`DWF_PI_COMMAND` к Durable не переносится. Продуктовую реализацию агент тестов
не создаёт. Материалы эксперимента прочитаны, соседний проект не изменён.

Выбран один необязательный путь к ESM-модулю, который возвращает обычный
`Provider` из `@earendil-works/pi-ai` 1.0.2. Это граница только модели: Durable,
владелец исполнения, постоянное хранение и CLI остаются настоящими. В управляемом
прогоне модуль возвращает штатный `fauxProvider` с удерживаемой фабрикой ответа;
в настоящем прогоне он прозрачно оборачивает выбранный встроенный провайдер.
Не нужен реестр плагинов, замена Harness или второй движок.

### Согласованные настройки продукта

| Настройка | Что передаёт тест | Что должен сделать продукт |
| --- | --- | --- |
| `DWF_STATE_DIR` | Абсолютный временный каталог состояния вне рабочего проекта | Поместить собственные данные запуска, Durable, IPC и служебные файлы в этот каталог; все клиенты используют его |
| `DWF_PLANNER_MODEL` | JSON `{"provider":"dwf-acceptance","modelId":"planner"}` в управляемом прогоне; явную настоящую пару provider/modelId в интеграции | Использовать эту модель планнера без молчаливой подмены |
| `DWF_MODEL_PROVIDER_MODULE` | Абсолютный путь к управляемому модулю или модулю наблюдения | Загрузить фабрику в процессе исполнения до выбора модели и открытия Durable; зарегистрировать только возвращённый модельный провайдер |
| `DWF_AUTH_SOURCE` | `pi` для согласованного настоящего прогона; управляемый прогон сохраняет изоляцию | В явном режиме pi использовать штатную команду авторизации установленного pi; без настройки сохраняется авторизация из окружения |
| `DWF_PLANNER_REASONING` | `medium` для выбранного пользователем прогона | Передать уровень в `agent.thinkingLevel`; наблюдатель независимо проверяет запрос |

Последние две настройки согласованы 2026-10-10 после выбора настоящей модели.

Точная сигнатура согласованного модуля:

```js
export function createProvider({ baseProvider }) {
  // Возвращает Provider из @earendil-works/pi-ai 1.0.2.
}
```

`baseProvider` — штатный провайдер с ID из `DWF_PLANNER_MODEL`, либо `undefined`,
если тест добавляет свой провайдер. Фабрика возвращает Provider с тем же выбранным
ID; продукт регистрирует его через `models.setProvider()` и затем разрешает modelId.
В режиме наблюдения отсутствие штатного провайдера — ошибка настройки, без fallback
на управляемые ответы. Без пути к модулю используется обычный провайдер продукта.
Модуль не получает Durable, хранилище, workflow или функции управления запуском.

`DWF_ACCEPTANCE_CONTROL_DIR` и `DWF_ACCEPTANCE_TOKEN` — окружение самих тестовых
модулей, не новый API движка. Продукт только сохраняет его при запуске своих
процессов. Тестовый модуль сам пишет сигналы и свидетельства; продукт не читает
их и получает ответ исключительно через настоящий модельный вызов Durable.

### Управляемый прогон и независимое наблюдение

Управляемый провайдер в начале фактического вызова сохраняет сигнал готовности
в виде записи received с тестовым user-поручением, хешем реально полученных messages, ID вызова,
provider session ID и PID процесса исполнения. Он ждёт явного `release`, учитывая
отмену вызова. Только после фактического выхода `start`, сверки поручения и
отсутствия готового результата через новый `inspect` тест выдаёт разрешение.
Ответ создаётся затем с новым случайным nonce и хешем этого поручения;
свидетельство содержит точный текст и `stopReason: "stop"`.

В настоящем прогоне провайдер-наблюдатель пересылает модель, сообщения, параметры,
отмену и события штатного адаптера без изменения. Он отдельно фиксирует полученное
тестовое поручение и терминальный ответ из настоящего модельного потока. Проверка
сопоставляет идентичность вызова, выбранную модель, `stopReason: "stop"` и точный
текст с результатом новых процессов `dwf inspect`. Свидетельство пишет тестовый
наблюдатель, а не лог продукта; приёмка не читает БД.

Наблюдатель также фиксирует безопасные данные о лимите: model.maxTokens,
contextWindow, переданный maxTokens и, через поддерживаемое штатным адаптером
наблюдение payload, фактически отправленное ограничение ответа. Проверка сверяет
его со штатным расчётом pi-ai для этой модели и контекста. Параметры не изменяются,
произвольный уменьшенный лимит не вводится. Положительный ответ должен нормально
завершиться; полезность плана по-прежнему оценивает человек.

Проверка предложения по интерфейсам 1.0.2 не выявила принципиального препятствия.
Существенная деталь наблюдателя: `streamSimple()` синхронно возвращает исходный
`AssistantMessageEventStream`, а итог можно наблюдать через его `result()`.
Второй `for await` того же потока недопустим: он отбирает события у Durable.
Нужно сохранить контекст вызова штатного провайдера, отмену и существующие
callbacks. Наблюдение `onPayload` не должно изменять payload или терять результат
ранее установленного callback. Эти условия проверены самопроверками harness;
интерфейс согласован в Q25, прозрачность проверена самопроверками harness.
Источник: [реализация потока pi-ai 1.0.2](https://github.com/earendil-works/pi/blob/v1.0.2/packages/ai/src/utils/event-stream.ts).

После получения результата тест останавливает процессы исполнения своего запуска,
сохраняет временные данные и читает тот же результат новым `inspect`. Сравнение
текста сохраняет пробелы и переводы строк; снимок рабочего проекта проверяет
отсутствие изменений файлов. RPC убран из Gherkin и задания планнеру
согласно согласованному подключению.

Сам Durable 1.0.2 может завершить submission ответом с `length`. Поэтому его
терминальный статус не заменяет независимую проверку `stopReason: "stop"`.
Это не определяет продолжение, восстановление или итоговый статус продукта
после обрыва: такие решения остаются открытыми.

### Изоляция, очистка и целевая поломка

Каждому сценарию нужны отдельные временные каталоги проекта, состояния и
свидетельств с закрытыми правами доступа. В тестах настоящая модель использует
явный выбор и авторизацию из окружения; пользовательские файлы настроек и
авторизации не открываются и не перезаписываются. Обычную авторизацию продукта
вне этих тестов предложение не определяет. Отсутствие модели/авторизации при
запуске интеграции — техническое препятствие, не пропуск или замена провайдера.

В отчёты попадают только разрешённые поля: тестовое поручение, идентификаторы,
хеши, выбранная модель, ограничения ответа и итоговый текст. API-ключи, headers,
credentials, полное окружение, произвольные payload и необработанный stderr
не сохраняются. After адаптирован: сырые stdout/stderr клиентов не публикуются.

Очистка должна учитывать отделившиеся процессы по уникальной наследуемой метке
теста. Перед каждым сигналом проверяются принадлежность текущему пользователю
и тесту, PID и время рождения; затем SIGTERM, ограниченное ожидание и при
необходимости SIGKILL. Удаляется только каталог, созданный данным тестом, после
остановки процессов. Очистка выполняется в finally и при ошибке проверки.

Для эксперимента с поломкой received даёт identity процесса, действительно выполняющего
удержанный модельный вызов. Временная правка продукта после получения received
возвращает нормальный runId и при выходе клиента прекращает именно этот процесс.
Тест проверит жизнеспособность исходного исполнителя до разрешения, чтобы новый
процесс, запущенный вызовом inspect, не скрывал прекращение прежней работы.
Проверяющий скрипт должен распознавать это конкретное нарушение независимости,
а не только произвольный таймаут. Сохраняются три фазы успех → поломка → успех
и неизменность тестов между ними; работа над восстановлением этим не задаётся.

обработки streaming/авторизации; сложнее сохранять выбор разных настоящих
провайдеров. Для одного сценария рекомендуется узкий модуль обычного Provider.

Проверены исходники и опубликованные интерфейсы именно 1.0.2:

[штатный fauxProvider](https://github.com/earendil-works/pi/blob/v1.0.2/packages/ai/src/providers/faux.ts),
[модельное исполнение Durable](https://github.com/earendil-works/pi/blob/v1.0.2/packages/durable/src/harness/generation.ts).

До адаптации 2026-10-06 фактически выполнены существующие команды:

## Исследование и план первой реализации

**Q26 согласовано 2026-10-10 после исследований ниже.** Штатные `pi --session` и
`--resume` читают native JSONL и создают исполнителя из сохранённой истории,
а не подключаются к работающему владельцу Durable. Форматы native pi и Durable
различаются. Это следует из установленного coding-agent 1.0.2
(`dist/main.js`, `dist/core/sdk.js`, `docs/session-format.md`).
В [официальном анонсе Durable](https://earendil.com/posts/pi-durable/) описаны API

в том же процессе; экспериментальный server/client работает из исходников
и не входит в опубликованный поддерживаемый интерфейс pi
([CHANGELOG v1.0.2](https://github.com/earendil-works/pi/blob/v1.0.2/packages/coding-agent/CHANGELOG.md)).
Готовое подключение штатного pi к любому участнику нашего workflow не подтверждено.
Выбор Durable в Q24 состоялся без проверки этого требования. После исследования
пользователь в Q27 согласовал подключаемый интерфейс на компонентах pi к живому
разговору; неизменённый CLI не обязателен. Это снимает неоднозначность требования,
но не доказывает готовность интеграции. Основа первого сценария остаётся Durable.

Ранее предложенный кандидат для узкого опыта — обычный pi TUI в сохраняемой терминальной сессии
(для опыта доступен `screen`) с небольшим расширением dwf для структурированных
команд и событий. Публичный API pi 1.0.2 предоставляет `sendUserMessage`, `abort`
и `agent_settled`; терминальный экран не становится API продукта. Нужно проверить
вход в тот же живой процесс, фактическую остановку и новое поручение с прежним
контекстом, отсоединение без гибели агента и получение результата другим клиентом.
Штатный `steer` ждёт границы текущего хода/инструментов и сам по себе не доказывает
требуемое прерывание. Опыт не выполнен; замена Durable этим ещё не согласована.
После обсуждения swarm этот вариант снят с рекомендации как основа:
сам доступ к сессии не требует процесса и постоянно работающего TUI на участника.

### Проверка масштаба: много сессий в одном процессе, 2026-10-08

Пользователь привёл swarm из 500 исследователей и уточнил ожидание одного
или нескольких процессов. Это не согласованный предел производительности:
типичная нагрузка исследователя пока не определена. Отдельный независимый
исследователь с полным доступным контекстом и отдельный проверяющий UI изучили
SDK/Durable. `createAgentSession()` создаёт самостоятельный AgentSession внутри
процесса; CLI и TUI на каждого участника не требуются. Общий код библиотек
загружается один раз, изменяемые контексты и runtime расширений должны оставаться
раздельными. Общий процесс уменьшает накладные расходы и объединяет область отказа.

Вне продукта выполнен ограниченный [опыт SDK](../project-creation/experiments/pi-sdk-swarm/probe.mjs)
на установленном 1.0.2/Node 26.8.1. [Результаты](../project-creation/experiments/pi-sdk-swarm/result.json):
500 настоящих сессий, 500 одновременно удержанных вызовов faux Provider,
500 правильно адресованных ответов и событий окончательного завершения.
Снимки RSS всего процесса после принудительной сборки мусора:

| Условия | RSS, МиБ |
| --- | ---: |
| Одна сессия без начальной истории, SDK уже загружен | 128,4 |
| 500 сессий без начальной истории, до поручений | 142,4 |
| 500 сессий одновременно ожидают управляемый ответ | 169,9 |
| Те же 500 ожидающих сессий, по 64 КиБ исходной истории на каждую | 240,2 |

Это не замер 500 реальных исследований: нет внешней сети, инструментов, браузеров,
MCP, UI, постоянного хранения и steering. История — уникальная ASCII-строка.
Измеряется весь пробник; faux Provider также расходует память и после ответа
кэширует сериализованные запросы. RSS одной сессии нельзя умножать на 500 для
оценки отдельных процессов. Методика и ограниченный вывод независимо проверены.
Пользовательские файлы настройки pi не использовались, окружение запуска очищено;
ModelRuntime при регистрации проверяет доступность провайдеров, что может включать
проверку существования стандартного файла авторизации. Реальных модельных вызовов нет.

Durable тоже поддерживает множество conversations в одном Harness, SQLite и
подключение наблюдателя к уже работающему разговору. Его не следует отвергать
из-за предположения, будто native UI обязательно требует отдельного процесса.
При этом готового штатного attach к pooled-сессиям SDK/Durable в pi 1.0.2 нет.
`InteractiveMode` может использовать существующий runtime, но выход/переключение
и показ уже идущего ответа требуют отдельной интеграции. Публичный `switchSession`
прерывает старую сессию; стандартный выход UI завершает процесс.

Дополнительно проверен опубликованный 1.1.0 от 2026-10-07 без установки.
Ограничения native UI сохранились. В Durable добавлены кэширование контекста
и `settings.contextRetentionMs`: по умолчанию 10 минут после простоя, `0`
освобождает кэш при простое. Это управление кэшем, не удаление истории и не
гарантия нулевой памяти неактивного агента. В coding-agent событие `agent_settled`
получило признак `aborted`. [Changelog Durable](https://github.com/earendil-works/pi/blob/v1.1.0/packages/durable/CHANGELOG.md),
[changelog coding-agent](https://github.com/earendil-works/pi/blob/v1.1.0/packages/coding-agent/CHANGELOG.md).
Приведённые замеры относятся только к установленному SDK 1.0.2.

### Согласованное хранение и исполнение, Q26

**Второй вариант ниже согласован пользователем 2026-10-10.** Первоначальный план
реализатора предусматривал процесс на запуск, SQLite и отдельный атомарный JSON
с состоянием/результатом. 2026-10-09 пользователь запросил дополнительное
исследование, включая независимого агента Astra с reasoning xhigh.

Исследование разделило три решения: число процессов, источник сохранённого
результата и способ чтения. Процесс на workflow не требует отдельной копии ответа.

| Вариант | Выигрыш | Цена |
| --- | --- | --- |
| Процесс и БД на workflow, отдельный JSON для `inspect` | CLI не зависит от SQL-формата Durable | Две записи; после аварии готовый ответ может остаться только в БД, а JSON — отстать |
| Процесс и БД на workflow, узкое чтение SQLite в режиме read-only | Один сохранённый источник ответа; `inspect` не требует живого исполнителя | Зависимость от схемы и формата записей закреплённой версии Durable |
| Общий сервис, чтение и управление через него | Единый владелец и подключение клиентов; можно размещать много workflow в процессе | Жизненный цикл сервиса, протокол и общий отказ; чтение при остановленном сервисе требует отдельного решения |

Независимый Astra рекомендовал второй вариант; основной агент после проверки
исходников и малого опыта пришёл к тому же выводу. Для первого сценария:

- Один фоновый владелец на workflow, внутри которого могут работать многие
  участники. 500 отдельных workflow при таком размещении означали бы 500 владельцев;
  это ограничение, а не обещание масштабирования между workflow.
- Свой каталог `~/.dwf/runs/<runId>/` и SQLite; `DWF_STATE_DIR` заменяет корень.
  `start` подтверждает приём только после сохранения поручения в Durable.
- `inspect` читает конкретное исходное поручение и связанный с ним ответ через
  `node:sqlite` с `readOnly: true`, не открывает Harness и не возобновляет задачи.
  Отдельный JSON с копией результата не нужен. Метаданные адресации/владельца
  не должны создавать обязательную вторую запись после принятия поручения.
  Возможная минимальная адресация: публичный `ROOT_CONVERSATION_ID` и стабильный
  `requestId` первого поручения, вместо поиска последнего assistant-сообщения.
- Будущий живой UI обращается к владельцу через API Durable; SQL-чтение результата
  не заменяет интерфейс наблюдения и steering. Его протокол сейчас не выбирается.

В установленном 1.0.2 `Harness.open()` изменяет пережившие перезапуск задачи
`running` на `pending`; открытие SQLite Storage выполняет миграционные записи.
Оба пути не являются нейтральным read-only просмотром. Сам SQLite допускает
отдельного читателя; финальный ответ и ссылка на него из submission сохраняются
одним commit Durable. Поэтому узкое чтение может убрать окно второй публикации.

Основной агент выполнил одноразовый опыт во временном каталоге: настоящий
Durable/SQLite и удерживаемый faux Provider, чтение отдельными Node-процессами.
До ответа прочитано `placed` без результата; после ответа — `done`, `stop` и
точный текст; после закрытия Harness — тот же результат. Попытка записи из
read-only соединения отклонена, модель вызвана один раз, временные данные удалены.
Это проверка осуществимости чтения, не продуктовая приёмка и не тест аварии.
Следующая предложенная проверка этой границы — остановить владельца до и после
финального commit и прочитать исход отдельным процессом, не вызывая модель снова.
Она ещё не выполнена. Потеря подтверждения `start` после commit также возможна;
автоматическое повторение запуска этим предложением не вводится.

Цена рекомендации явная: SQL-формат не является стабильным публичным API просмотра
Durable. Нужны закреплённая версия, проверка схемы и структуры прочитанных записей;
при обновлении — отдельная проверка совместимости. Одного номера SQL-схемы
недостаточно для гарантии неизменности JSON-записей. Универсальный читатель истории,
документов и графа не предлагается.

При нетерминальном поручении сохранённое состояние не доказывает, что исполнитель
жив. Рекомендуется проверять его идентичность и повторно читать финал после
обнаружения завершившегося владельца, чтобы не получить ложную ошибку из-за гонки.
Если финала нет, не показывать бесконечное исполнение и не запускать модель
из `inspect`. Впоследствии пользователь отдельно согласовал Q30: `failed`
с понятной причиной, без результата и перезапуска, если полного финала нет.
